あなたは今 **下流(fork)** として、上流リポの変更取り込みと **DOWNSTREAM NOTICE**(追随対応の通知、`.notices/*.md`)への対応を行います。この仕組みは任意の上流→下流(T1→T2, T2→T3 等)で使われます。notice を書くのは上流側の `/ship` で、書く欄と読む欄は `.notices/README.md` のスキーマで揃っている。仕様詳細: `.notices/README.md`

## 付属ファイル(条件に当たったら必ず読む。読まずに進めない)
このフォルダの次のファイルは、条件に当たる fork・区間でだけ必要な規則を持つ。本文の各所にある `→ relay.md` / `→ moved.md` はそこへの参照。
- **`relay.md`**(中継・3 段以上の Tier): 次のいずれかに当たったら、区間の組み立ての前に読む:
  - 直上 upstream が中間 Tier(下記「自 fork の識別と台帳」5)
  - ツリー内(適用済みを含む)・流入予定の notice のどれかが `covers:` を持つ
  - 自分が下流を持つ fork、またはそうか読み取れない(`.claude/rules/project.md` の TIER 節)
  - モードが `status --chain` または `relay`
- **`moved.md`**(移動・改名の移植): 次の区間の notice(covers 側・covered 側を含む)のどれかに `moved:` があれば、その区間の詳細計画(手順 2)の前に読む。
- notice id モード(偵察・区間の組み立てを行わない): 対象 notice と自 fork について同じ条件を判定し、当たれば手順 5 の前に読む。

## 大原則
- **状態はイベントではなくファイルと履歴から導出する**: 「ツリー内に存在する現役 notice の集合」−「継承済み notice の集合(fork 成立点から自動判定、下記)」−「自 fork 台帳に記録済みの集合」= 未適用。merge が誰の手でいつ行われたかは問わない(手動 merge / GitHub 上の merge / このコマンドの merge、すべて同じに扱う)。
- **詳しく計画するのは次の区間だけ、承認は区間ごと**(既定)。残りの区間は 1 行ずつの概観(どこまで進めるかを人間が決める材料)にとどめ、notice の全文・上流の変更点・衝突の予測・移植・fork 側の追従箇所は**次の区間の分だけ**調べて計画にする。起動時に幅(`<n>`)を指定されたときは、「次の区間」を「次のまとめ」(1 回の承認で進める連続した区間。下記「まとめ」)に読み替える。先の区間の材料は読まない(context を埋め、目の前の区間の判断に混ざるため。先の区間の詳細はその前の区間の merge で変わるので、事前に詰めても価値が低い)。
- **区間の終わりで止まり、次の区間の計画を出して待つ**。承認後、その区間の merge・コード修正・DB 操作・バックフィル・検証・台帳記録・コミット・push までは途中確認なしで進め、区間を終えたら結果と**次の区間の詳細計画**を報告して待つ。その報告への `go` = 次の区間の計画の承認(止まる回数は 1 区間 1 回のまま)。区間の終わりの返事は `go` / `go last` / `再計画` / `ここで終える` の 4 つだけで(`go last` = 見せた計画の区間を進めたら、次の計画を作らずに今回の出撃を終える。下記「go last」。`再計画` = 何も進めずに次の区間の計画を作り直して聞き直す。下記「再計画」)、どこまで進めるかの幅は起動時の引数で決める(偵察の後に範囲を広げ直さない。広げたいときは「ここで終える」の後に幅を付けて起動し直す)。止まらずに進めるのは `all` を付けたときだけで、そのときは区間ごとに「計画 → 実行」を繰り返す(計画をまとめて先に作らない)。どちらでも**下記「停止条件」と「重い区間」に当たったら停止を優先する**(承認は「計画どおりなら進めてよい」であって「何が出てきても押し切れ」ではない)。
- **区間単位で進める**: 未適用 notice を区切り(`checkpoint:`)ごとの区間に分け、区間ごとに「merge → 適用 → verify → 台帳 → commit → push」を完結させる。**既定は notice 1 件 = 区切り 1 つ**(`checkpoint: -` と上流が例外宣言した notice だけが次の区切りまで同じ区間に入る。欄が無い旧 schema は区切り扱い = 安全側)。途中で止まっても fork は直前の区切りに居て、再実行すれば続きから進む(状態は集合演算で導出されるので追加の記録は不要)。
- **区間ごとに fork をクリーンに揃える**: 区間を commit するとき、その区間の上流の変更に fork 側のコードが追従しきっていること。notice があるかどうかは問わない(上流が notice を出し忘れた変更も同じ)。部品・lib・core の使い方が変わったら、fork 内の使用箇所を全部探して新しい使い方に揃える。「古い使い方のままでも動くから残す」はしない。残すのはユーザーが判断したときだけで、理由を台帳に残す(下記「上流の変更点の洗い出し」、手順 6)。
- **適用計画の承認 = DB 操作を含む全ステップの明示的実行指示とみなす**。このスキル実行中は「DB 操作はユーザーに依頼する」系の一般ルールより本規約が優先される。ただし対話プロンプトを出すコマンド(`[user-run]` マーカー付き、db push 等)だけは Claude では実行できないため、下記の in-session ユーザー実行で合流する。

## 停止条件(完走原則より優先)
区間の merge / 適用中に次のいずれかに当たったら、**その区間を commit せずに止めて報告する**(前の区間は commit 済みなので fork の整合は保たれる):
- 上流の変更がこの fork の固有ロジックやデータを壊す: merge で fork の挙動が消える / `[user-run]` の db:push 差分に DROP・列削除などデータ消失が含まれる / notice の手順が fork 固有のテーブル・ファイルを触る
- notice の `required_actions` と実態が食い違い、verify が通らず、直し方が自明でない
- `moved:` の移植(→ moved.md)で、fork の編集の一部を新しいパスに当て直せず、直し方が自明でない
- 上流の変更自体にバグや設計上の問題が見え、そのまま入れると fork が退行する
- fork の `.claude/rules/project.md` の制約・事業上の意図と矛盾する
- 判断が本当に割れるコンフリクト(従来どおり)
- 上流の変更に fork の使用箇所を揃えきれない(新しい使い方への寄せ方に fork 固有の判断が要る・寄せると fork の挙動が変わる)。黙って古い使い方を残して commit しない
- 区間の検査(手順 6 の typecheck / lint)が落ち、直し方が自明でない(既知の失敗は除く: 下記「修正(fixes)」)
- merge 結果が区間の上流差分の外のファイルを変えた(手順 5d「区間外変更の検査」。git の改名推定が fork の無関係なディレクトリへ上流ファイルを流し込む・fork のファイルを消す等)

止まり方: merge 途中(未 commit)なら `git merge --abort` で区間開始前に戻す。適用途中なら変更をそのまま残し、何を変えたかを示す。そのうえで「何を見つけたか / 根拠(ファイル・差分・出力)/ 選択肢(この notice をスキップして次の区間へ・手で直して続行・古い使い方を残す(理由を台帳へ)・上流に報告して待つ)」を提示して**待つ**。勝手にスキップも押し切りもしない。再開はユーザーの指示で(同じセッションならその返事で、閉じた後なら `/flux` や notice id 指定で続きから)。

## 重い区間(`all` / まとめの途中でも、その区間の手前で止まる)
- 重い区間 = fork が移動元を編集している `moved:` の移植(→ moved.md)があり、その移植差分が大きい(目安: 合計数百行以上)か、fork 固有のロジック・データの扱いに触れるもの。
- 詳細計画に移植の中身(組ごとの移動元 → 移動先・ファイル数・行数・fork の編集の要点)を載せ、`all` の途中でも**その区間の merge の前で止めて**承認を取る(既定の流れではもともと区間の手前で止まるので、計画に中身を載せることだけが加わる)。まとめ(`<n>`)は重い区間を他の区間と一緒にしない: 重い区間の手前でまとめを切り、重い区間は単独で承認を取る。
- 区間の中で止める(移植だけ先に見せる)・notice の粒度の問題として上流に差し戻す、はしない。移植の重さは fork 側の編集で決まり上流には予測できず、出荷済みの commit は後から分けられないため。1 件の notice が重い移植を伴ったことは「上流への所見」(d) に 1 行出す。

## 修正(fixes)— 先に修正が控える区間
上流は、前に出荷したものの不具合を直す notice に `fixes: <notice id | commit:<sha>>` を書く(`.notices/README.md`「修正(fixes)」)。修正元の区切りは、そこで止まると既知の不具合を抱えた地点になる。
- **対応づけ**(区間の組み立て 5 で): 流入予定・ツリー内の各 notice の `fixes:` を読み、参照先の notice id はその notice の区間、`commit:<sha>` は merge 先の範囲(前の区間の merge 先 → その区間の merge 先)にその commit を含む区間を修正元の区間とする。参照先がどこにも見つからなければ報告する(黙って飛ばさない)。適用済み・継承済みの notice や、既に HEAD の祖先の commit が参照先なら「修正元は適用済み」。
- **修正元が未適用**: 概観で修正元の区間に「修正あり: 区間 K の <修正 notice>」と印を付ける。その区間の詳細計画の先頭に「この区間の <修正元> は区間 K の <修正 notice> で修正される」と出し、平文で「この区間を進めますか?(1 区間ずつ進める / ここで止める)」と聞いて待つ。`all`・`light`・まとめの途中でもここは止まる(承認なしで通り過ぎない)。区間は自動でまとめない(本番へのデプロイ方法は fork ごとに違い、ユーザーが知っているため。push が本番に出るなら止める判断はユーザーがする)。
- **修正元の区間の検査で落ちたもの**: 修正 notice のコミットが触るファイル(`git diff --name-only <修正 notice の区切り点>^ <修正 notice の区切り点>`、commit 指定ならその commit)に当たるものは「既知(修正は区間 K)」として台帳の `notes:` に書いて commit してよい(停止条件にしない)。それ以外の失敗は通常どおり。
- **先回りしない**: 修正が先にあると分かっていても、その区間で同じ修正を実装しない(後の merge で衝突し、fork 独自の版が残る)。
- **修正元が適用済み**: 止まらない。概観で修正の区間に「適用済み <修正元> の修正」と印を付ける(本番に不具合が出ているかもしれないので、ユーザーが優先度を決める材料)。その区間の詳細計画では、台帳の修正元の行の `notes:` と fork 側の差分から当時の回避策を探し、修正が入った後に要らなくなるものを掃討の対象に載せる。
- **報告**: 区間の終わり・最終報告で、今の位置が修正元を通った後で修正の手前なら「既知の未修正あり: <修正元>(修正は区間 K)。この位置でのデプロイに注意」を 1 行出す。

## 軽い区間(`light` の判定。計画を詳しく作った区間だけ)
- 軽い区間 = 次のどれにも当たらない区間。1 つでも当たれば軽くない: merge と `moved:` の移動以外の作業がある(notice の required_actions に fork 側の変更がある)/ 衝突の事前予測に 1 件でもある / `[user-run]` がある / DB(スキーマ・db:push・データ移行・バックフィル)に触れる / 「上流の変更点の洗い出し」で揃えるものがある / 「上流が持つパスでの fork の編集の見直し」が「なし」でない / 重い区間 / 修正元が未適用の区間(上記「修正(fixes)」)。
- 判定できるのは詳しく計画した区間だけ(次の区間・次のまとめ)。概観の残りの区間には付けない(材料を読んでいないため)。
- 計画に「この区間は軽い(根拠: 上の各項目がなし)」と 1 行書き、PLAN FILE の SEGMENTS の行に `light` を付ける(fleet の見直しが「この先 N 区間は軽い」と数える)。

## 上流への所見(findings)— 最終報告の常設項目
適用中に気づいたことを集め、最終報告の末尾に「**上流への所見**」として必ず出す(無ければ「なし」):
- (a) 上流のバグ・不備(取り込んだコードの問題、テスト漏れ)
- (b) notice と実態のズレ(手順が合わない、verify が通らない、書かれていない影響があった)。**notice が無いのに fork 側の追従が要った上流の変更**(下記「上流の変更点の洗い出し」で見つかったもの)は notice 漏れとして必ずここに出す(上流は「追従が要る変更には notice を出す」が必須)
- (c) この fork で必要になった修正のうち、他 fork でも同じ修正が要りそうな汎用性のあるもの(= /order <上流リポ> 候補)
- (d) 設計上の懸念

(a)(c) の文案を出す前に、上流で既に直っていないかを確かめる: 流入予定の notice の `fixes:`、その箇所のファイルに対する上流の未取り込みの commit(`git log HEAD..<upstream>/<branch> -- <file>`)。直っていれば文案は出さず「上流で修正済み(区間 K / commit <sha>)」と書く。

各項目: 1〜2 行 + 根拠(ファイル・commit・出力)+ 起票文案 1 行。**自動で /order は起票しない**。ユーザーが `/order <上流リポ>` を打てば会話文脈から起票できる形にしておく。台帳の `notes:` には逸脱だけを書き、所見は報告側に出す(台帳は fork の記録であって上流宛てではない)。

## 自 fork の識別と台帳
1. origin 取得: `git remote get-url origin`
2. fork-id 導出: URL のパス部分(ホスト以降)から `.git` を除去し、`/` を `--` に置換、小文字化。例: `git@github.com:acme/shop.git` → `acme--shop`。origin が無ければ `local--<ディレクトリ名>`。
3. 自 fork 台帳 = `.notices/applied/<fork-id>.md`。無ければ未適用ゼロ記録として扱う(初回適用時に作成)。
4. `.notices/applied/` 内の他の fork-id のファイルは中間 Tier や他 fork の台帳(merge で流れてきたもの)。**自分の状態と混同しない**。参考情報として読むのは可。
5. **中間 fork-id** = 直上 upstream の URL から同じ規則で導出した fork-id。`<upstream>/<branch>` に `.notices/applied/<中間 fork-id>.md` があれば、直上 Tier は自分自身も下流として上流を追随している中間 Tier(→ relay.md)。無ければ直上 upstream は最上流で、祖父 notice は存在しない。

## upstream の特定
1. `git remote -v` で origin 以外の remote(通常 `upstream`)を探す。
2. 無ければユーザーに upstream の URL を尋ね、`git remote add upstream <url>` してから続行する(勝手に推測しない)。
3. upstream のデフォルトブランチは `git ls-remote --symref <remote> HEAD` で特定する。

## 継承済み(pre-fork) notice の自動判定
fork は最新コードごと clone して始まるため、**fork 成立点のツリーに既に存在していた notice は定義上すべて適用済み**(継承済み)。これは台帳に記録せず、実行のたびに git 履歴から導出して未適用判定から除外する:
1. fork 固有の最初のコミット: `git rev-list --reverse HEAD ^<upstream>/<branch>` の先頭(= HEAD から辿れるが upstream に無い最古のコミット)。fetch 済みであること。
2. **無い場合**(fork がまだ何もコミットしていない)→ ツリー内の現役 notice は全件継承済み。
3. fork 成立点 = そのコミットに親があれば第一親(`<first_own>^`)、無ければ(ルートコミット = GitHub テンプレート起源等)そのコミット自身。
4. 継承済み集合 = `git ls-tree --name-only <fork成立点> .notices/` に存在する notice の id 群。
5. **shallow clone**(`git rev-parse --is-shallow-repository` が true)では履歴を辿れず判定不能。その旨を伝え、`git fetch --unshallow <upstream>` を提案するか、ユーザーに継承済み範囲を確認する(勝手に全件継承済み扱いしない)。
- 継承済み notice はファイル削除しない(下流で削除すると、上流がその notice を編集・done/ へ移動した際に merge で modify/delete コンフリクトになるため。判定式での除外が正)。

## モード分岐($ARGUMENTS)
- **空(既定)**: フルフロー(下記)。区間を 1 つ終えるごとに止まり、続行の指示を待つ(手順 4)。
- **`all`**: フルフローと同じだが、最初の区間の計画の承認だけを取り、以後は区間ごとに「次の区間の計画 → 実行」を止まらずに繰り返して最後まで進める(停止条件・重い区間では止まる)。区間の合間にアプリを確認しなくてよいとき・fleet で丸ごと任せるとき用。
- **`next`**: 既定と同じ(1 区間ずつ止まる)。以前の呼び方の別名として受け付ける。
- **`<n>`**(2 以上の整数): 幅 n。次の n 区間を「まとめ」として詳しく計画し、1 回の承認でまとめて進めて止まる。止まったときに出す次の計画も n 区間分(下記「まとめ」)。
- **`to <checkpoint ラベル | commit>`**(終点。幅と組み合わせられる: `<n> to <位置>` / `all to <位置>`): その位置に届く区間(merge 先がその commit を含む最初の区間)で今回の出撃を終える。承認の幅は付けた幅のまま(何も付けなければ 1 区間ずつ)。まとめ・`all` も終点の区間で切る。概観では終点の区間に印を付け、その先の区間は「今回の出撃の外」と書く。終点の区間を終えたら次の区間の計画は作らず、最終報告(手順 8)をして終了する(区間の終わりで `go` が来ても先へは進まない。続けるなら新しく起動する)。位置が上流の履歴に無ければ、そう言って止まり人の答えを待つ(推測しない)。既に取り込み済みなら、今回進むものは無いと報告して終える(取り込むものなし)。
- **`light`**(幅・`to` と組み合わせられる: `light` / `2 light` / `to <位置> light`): 区間の終わりで、次の区間の詳細計画が「軽い区間」(下記)なら承認を待たずにその計画で続ける(区間報告と次の計画の要点を 1〜2 行出す)。軽くない区間の手前では既定どおり止まって承認を取る。最初の区間の計画の承認はいつも取る。停止条件・重い区間・終点はそのまま効く。
- **`status`**: 状態報告のみ。fetch + 未マージコミット数 + 全区間の概観(手順 2 と同じ 1 行ずつ)+ 継承済み・台帳突合の結果を一覧表示して終了。**merge も適用も一切しない**(詳細計画も作らない)。
- **`status --chain`**: 祖父 notice ごとの中継状況の報告のみ(merge も適用もしない)。出力形式 → relay.md。
- **`relay`**: 中間 Tier が、中継判定の導入前に適用した未判定の旧 notice を中継 notice にまとめて下書きする(merge も適用もしない)。手順 → relay.md「relay モード」。
- **notice id / ファイル名**: その notice だけを対象に、フルフローの手順 5 以降を行う(merge は行わない。既にツリーに存在する notice が対象。区間分割もしない)。

## 未適用判定(ツリー内・流入予定の両方に同じ規則を適用)
notice は次のいずれかに該当すれば対象外、残りが**未適用**:
- `from:` の repo URL が自分の origin と一致(ssh/https 表記差・`.git` 有無は無視)→ 自分が上流として起票したもの。
- 継承済み集合(上記の自動判定)に含まれる → 適用済み扱い。
- 自 fork 台帳に id が記録済み → 適用済み。
- covered 側の id(`covers:` で他の notice にまとめられた id)→ relay.md の規則で判定する。

## 区間の組み立て
1. 未適用 notice を 2 群に分ける: **ツリー内**(`.notices/` 直下の `*.md`、`done/` と `applied/` は除外。前回の部分実行で merge 済みだが未適用のもの)と**流入予定**(`git diff --name-only HEAD...<upstream>/<branch> -- .notices/` のうち直下の `*.md`。内容は `git show <upstream>/<branch>:.notices/<id>.md` で読む)。
2. 流入予定の各 notice に**区切り点 commit** を対応づける: 通常は追加 commit `git log --diff-filter=A --format=%H <upstream>/<branch> -- .notices/<id>.md`(通常 1 件。複数なら最古)。祖父 notice の区切り点 → relay.md。`from: commit:` 欄は参考情報で、判定には使わない。
3. covered 側の notice は区切り点にせず covers 側の区間に入れる(→ relay.md)。
4. 残りの流入予定 notice を区切り点 commit の履歴順に並べる(`git rev-list --reverse --topo-order HEAD..<upstream>/<branch>` 上の位置。区切り点が既に HEAD の祖先なら区間 0 扱い)。
5. 区間を切る(全区間について行う。ここで読むのは区切りの判定に要る `checkpoint:`・`covers:`・`moved:`・`fixes:` の行と、一時許可の失効を示す `resolves:` の行だけで、notice の全文は読まない。流入予定は `git show <upstream>/<branch>:.notices/<id>.md` を `grep -E '^(checkpoint|covers|moved|fixes|resolves):'` で絞る):
   - **区間 0** = ツリー内の未適用 notice(merge 不要)。空なら無し。
   - 以降、流入予定を履歴順に走査し、**区切り notice**(`checkpoint:` が `-` 以外、または欄が無い旧 schema)の**直後で区間を閉じる**。閉じた区間の merge 先 = その区切り notice の区切り点 commit。`checkpoint: -` の notice は次の区切りまで同じ区間に入る(上流の例外宣言。理由は notes: にある)。
   - 最後の区切り以降の notice(無ければ空)+ 残りのコミットが**末尾区間**。merge 先 = `<upstream>/<branch>`。notice が無くても未マージコミットがあれば末尾区間は存在する(merge のみ)。
   - 結果として通常は notice 1 件 = 1 区間。同じ commit で出荷された複数 notice は merge 先が同じ区間が連続する(merge は 1 回目で完了し、2 回目以降は「既に最新」になるだけ。正常)。
6. 区間ごとに持つ情報(概観): 番号 / merge 先(短 sha と、checkpoint ラベル or `HEAD`)/ 含まれる notice id / そこまでのコミット数 / `moved:` の有無 / 修正の関係(上記「修正(fixes)」の印)/ `resolves:` のうち自分の一時許可(`.fork-ownership/<fork-id>.permits.txt` の `upreq:`)に当たる番号。当たる行は、その区間の merge の後に許可が失効する(全番号が解決した行)ので、計画で「受け口へ移す・元に戻す」を示す(`.notices/README.md`「解決(resolves)」、`pnpm ownership:check` が expired-resolved で示す)。衝突の予測・移動元の編集・上流の変更点は**次の区間だけ**(下記 2 節)。

## 衝突の事前予測(次の区間の計画時、読み取りのみ)
次の区間の merge で衝突しそうなファイルを承認前に出す。index・作業ツリーは変更しない。
1. 用語: `base` = `git merge-base HEAD <upstream>/<branch>`(その区間の計画時点の HEAD で求める)。**fork 側の編集** = `git diff --name-only <base> HEAD`。**区間の上流側の変更** = `git diff --name-only <base> <区間の merge 先>`。
2. git 2.38 以上(`git version`)なら正確に出せる: `git -c merge.directoryRenames=false merge-tree --write-tree --name-only HEAD <区間の merge 先>`(exit code 1 = 衝突あり、出力に衝突ファイル)。`-c merge.directoryRenames=false` は手順 5b の merge と同じ設定にして予測と実際をそろえるため。
3. 近似(2.38 未満): fork 側の編集と区間の上流側の変更の**共通部分**(両方を一時ファイルに書いて `comm -12` で突き合わせる)。近似であることを計画に明記する(同じファイルでも別の箇所なら実際は自動で解決される)。
4. 各ファイルに fork 側の編集規模 `git diff --stat <base> HEAD -- <file>` を添える。上流側の改名は `git diff -M --name-status <base> <区間の merge 先>` の `R` 行を添える。
5. 計画に「衝突しそうなファイル(fork 側の編集規模)」と「移動元の編集」(→ moved.md)を載せる。無ければ「なし」。

## 上流の変更点の洗い出し(次の区間の計画時と適用時。notice の有無を問わない)
notice は追従の最低線で、上流が出し忘れることもある。次の区間の上流の差分そのものから「fork 側の使い方に影響する変更」を拾い、fork 内の使用箇所を探して、その区間の計画に載せる。
1. 範囲: 区間の上流差分 = `git diff <base> <区間の merge 先>`(`base` は「衝突の事前予測」1)。対象は共有の部品・lib・hooks・utils・core(`src/components/` `src/lib/` `src/hooks/` `src/utils/` `src/features/core/` など、fork が import して使うもの)。
2. 拾うもの:
   - export の削除・改名、関数の引数・戻り値・props の型の変更(必須の追加、意味の変わった既定値を含む)
   - 新しく付いた `@deprecated`、互換のために残された shim・旧名の別名・旧パスの再 export(「互換」「deprecated」「legacy」「旧」などのコメントや、中身が新しい名前を呼ぶだけの関数)
   - 設定・規約の変更(config のキー、生成器の出力、命名・置き場の規則)で fork 側の書き方が変わるもの
3. fork 内の使用箇所を検索する(import している fork 側のファイル、旧名・旧パス・旧 props の grep)。上流から来たファイル自体は対象外(merge で揃う)。
4. 計画に「変更点 / fork 側の使用箇所 / 揃え方」を載せる。無ければ「なし」。notice の required_actions と重なるものは notice 側にまとめる。
5. merge で fork 側のツリーも変わる(衝突の解消・移植)ので、その区間の merge の後にもう一度 3 を行い、計画との差を手順 6 で埋める(新しく見つかったものも同じ区間で揃える)。

## 上流が持つパスでの fork の編集の見直し(次の区間の計画時)
merge と移植は fork の編集をそのまま運ぶ。運ぶ先が上流の持ち物なら、運ぶ前に「そこに置いてよいか」を見直す(衝突を解いて通すだけで終えない)。
1. 対象(この区間が触るものだけ。fork 全体の監査はしない): 衝突しそうなファイル / `moved:` の移動元で fork が編集・追加したファイル(→ moved.md)/ 区間の上流差分のうち fork も編集しているファイル。
2. 判定は自 fork の CLAUDE.md(CORE_FILES・`fork_core_edit_compat`・CODE_PLACEMENT の祖先 lib)と `src/lib/CATALOG.md` で行う。上流の持ち物(core、上流ルートの `_screen/` `_layout/` のドット付きでない名前、祖先リポの lib の内部など)に fork の編集・追加があれば、1 件ずつ次のどれかを計画に載せる:
   - a. **fork の持ち物の場所へ移す**: 隣のドット付きの名前(`<Name>.<project>.tsx`)・`_components/`・config の値・`override.ts`・fork 自身の lib など。機械的に移せて挙動が変わらないものはこの区間で移す(手順 6)。
   - b. **残して上流に拡張点を頼む**: 上流に差し込み口が無く、移すと挙動が変わるもの。`fork_core_edit_compat` を満たす形で残し、「上流への所見」(c)/(d) に /order <上流リポ> の文案を出す。
   - c. **残す**: 人が以前に決めて残している編集など。理由を書く(手順 8 の `kept_old:`、台帳の `notes:`)。
3. 該当が無ければ計画に「なし」の 1 行。どれにするかの判断は計画への go で決まる(迷うものは選択肢を並べて聞く)。

## まとめ(幅 `<n>` で起動したとき)
- まとめ = 1 回の承認で進める連続した区間。幅 n なら次の n 区間(残りが少なければそこまで。終点 `to` があればその区間で切る)。重い区間の手前で切る(重い区間は単独)。
- 計画: まとめの各区間について、手順 2 の詳細計画を区間ごとに分けて載せる(notice・適用計画・衝突の予測・上流の変更点・所有の見直し)。2 区間目以降の衝突の予測と使用箇所は、前の区間の merge 先を起点に読み取りだけで求め(`git merge-tree` の起点を前の区間の merge 先にする)、「前の区間の結果しだいで変わりうる」と添える。
- 承認: 平文で「区間 k〜m/N をこの計画で進めてよいですか?(go / go last / いいえ)」。go はまとめの全区間の計画の承認(go last はまとめの全区間を進めて終える)。
- 実行: 区間ごとに手順 5〜7 を完結させる(区間ごとに commit・push・台帳)。2 区間目以降は merge の前に計画どおりか確かめる(HEAD が前の区間の commit・作業ツリーがクリーン・衝突しそうなファイルと fork 側の使用箇所が計画と同じ)。違えばそこで止まり、その区間からの計画を作り直して差分を示し、承認を取り直す。停止条件はまとめの途中でもそのまま効く。
- まとめの終わり: 手順 4 の「区間の終わり」と同じに止まる(区間報告はまとめの全区間分、次の計画は次のまとめ)。

## フルフロー
1. **偵察**: `git fetch <upstream>` → 未マージコミット数(`git rev-list --count HEAD..<upstream>/<branch>`)→ 上記「区間の組み立て」(全区間の概観まで)。working tree に未コミットの変更がある場合は先に報告し、stash してよいか確認する。
2. **概観と次の区間の計画**:
   - **概観**: 残りの全区間を日本語で 1 行ずつ(区間番号 / merge 先の短 sha / checkpoint ラベル / notice id、重い区間の見込み・修正の関係があれば印)。継承済みとして除外した件数があれば 1 行添える。今日どこまで進めるかを人間が決める材料なので、これ以上は書かない。
   - **次の区間の詳細計画**: 次の区間(区間 0 があれば区間 0)の notice だけを全文読み(流入予定は `git show` で)、required_actions を**自リポの実情に写像した適用計画**(対象ファイル・コマンド・順序・`[user-run]` 合流点・verify 手順)にする。「衝突の事前予測」「移動元の編集」(→ moved.md)「上流の変更点の洗い出し」「上流が持つパスでの fork の編集の見直し」(上記。notice の無い merge だけの区間も対象)を載せる。重い区間(上記)なら移植の中身も載せる。
   - **乖離の掃討を計画に含める**: required_actions は最低線。notice の変更点・目印(grep パターン等)で fork 全体を検索し、旧仕様のまま残る fork 固有コード(required_actions に無いもの)も対象ファイルとして計画に載せる。
   - 未適用ゼロ・未マージコミットもゼロなら「この fork の追随対応はすべて完了しています」で終了。未適用ゼロで未マージコミットだけある場合は merge のみの計画(末尾区間 1 つ)。
3. **承認を取る**(次の区間の計画に対して。まとめのときは上記「まとめ」)。平文で「区間 k/N をこの計画で進めてよいですか?(go / go last / いいえ)」。
4. **区間ループ**: 承認された区間で手順 5〜7 を**完結**させる。失敗したら取り繕わず止める(fork は直前の checkpoint に整合した状態で残る。再実行すれば残り区間から続く)。
   - **区間の終わり**(既定): `git fetch <upstream>` をやり直し、次の区間について手順 2 の詳細計画を作る(概観は前回から変わった点だけ)。手順 8 の区間報告 + 次の区間の詳細計画を出し、平文で「次の区間 k+1/N をこの計画で進めますか?(go / go last / ここで終える)」と聞いて**待つ**。go → その計画で次の区間 1 つ(まとめなら次のまとめ)。go last → 下記「go last」。終点(`to`)の区間を終えたときは次の計画を作らず、聞かずに最終報告(手順 8)をして終了する。ここで終える → 最終報告(手順 8)をして終了(残りは次の `/flux` で続きから。幅を変えたいときもそこで起動し直す)。それ以外の返事(「あと 2 区間」など)は計画の外なので受けず、「ここで終えて `/flux <n>` で起動し直してください」と答えて待つ。
   - **go last**(手順 3 の承認と区間の終わりの返事。go と同じ承認で、同じ計画ファイルに結び付く): go と同じに確かめて、その計画の区間(まとめなら全区間)を進める。進め終えたら fetch も次の区間の計画もせず、聞かずに最終報告(手順 8)をして今回の出撃を終える(終点 `to` の区間を終えたときと同じ終わり方。残りは次の `/flux` で続きから)。確かめで計画を作り直したときは、作り直した計画を示して改めて承認を取る(前の go last は作り直した計画を承認しない)。
   - **再計画**(手順 3 の承認と区間の終わりの返事。上流が計画の土台を変えたとき — 計画の後に次の区間の notice が書き換わったなど。checkpoint で閉じる区間は merge 先が固定なので、下の「go を受けたとき」の確かめでは気づかない): merge・適用・commit はしない。`git fetch <upstream>` をやり直して概観を作り直し、次の区間の notice を上流の先端で読み直して(`git show <upstream>/<branch>:.notices/<id>.md`)手順 2 の詳細計画を作り直す。前の計画との違いを 1〜2 行で示し、同じ問いで改めて聞く(手順 3 なら go / go last / いいえ、区間の終わりなら go / go last / ここで終える)。前の go・go last は作り直した計画を承認しない。直前の区間の報告(手順 8)はやり直さない(その区間の結果はそのまま)。
   - **go を受けたとき**: HEAD が直前の区間の commit のまま・作業ツリーがクリーン・(次の区間が末尾区間なら)上流のブランチの先頭が計画時のまま、をすべて満たせばその計画で進む。checkpoint で閉じる区間の merge 先は固定の commit なので、上流が先に進んでも計画は変わらない。どれかが違えば次の区間の計画を作り直して差分を示し、承認を取り直す。
   - `all`: 区間の切り替わりで「区間 k/N 完了(checkpoint: <label>)」と次の区間の計画の要点を 1〜2 行報告し、止まらずに次の区間の計画 → 実行へ進む。次の区間が重い区間・修正元が未適用の区間なら手前で止まって承認を取る。終点(`to`)があればその区間で終える。
   - `light`: 区間の終わりで次の区間の詳細計画を作り、軽い区間(上記)なら `all` と同じに 1〜2 行報告して承認なしで進む。軽くなければ既定どおり止まって承認を取る。
   - **会話が途切れても再開できる**: 区間の終わりで止まっている状態は台帳と git から導出でき、手順 8 の区間報告が残りの判断材料を持つので、セッションを閉じた・compact した後でも `/flux` を打ち直せば次の区間の計画から続く。
5. **merge**(区間 0 は省略):
   a. 準備: 区間に `moved:` の移植対象があれば先に差分を保存する(→ moved.md 手順 2)。merge 直前の HEAD を控える(`git rev-parse HEAD` = `<pre>`)。
   b. `git -c merge.directoryRenames=false merge --no-commit <区間の merge 先>`。ディレクトリ改名推定を切るのは、fork 側の削除・再編を「ディレクトリの改名」と誤推定し、上流の新規ファイルを fork の無関係なディレクトリへ置いたり fork のファイルの削除をステージしたりするため(`-X no-renames` では止まらない)。上流の本物のディレクトリ移動は `moved:` の移植が扱う。移植対象があればここで移植する(→ moved.md 手順 3〜4)。
   c. コンフリクトは自分で解消する(上流の意図と自 fork の改変の両立を判断。判断が本当に割れるものだけユーザーに確認)。プロジェクトごとのファイルの採り方:
      - `.claude/rules/project.md` と `behavior.md`: fork 側を採り、上流の追加はこの fork に当てはまるものだけ取り込む。
      - `.claude/rules/shortcuts.md` と `term-aliases.md`: `fork entries below` マーカーより上を上流側、下を fork 側で採る。
      - 生成物 `src/app/route-map.txt`(ルート地図): 衝突しても手で直さない。どちらかの版を採って他の衝突を先に解消し、最後に `pnpm routes:map` で作り直して `git add` する。衝突が無くても、区間の上流差分にこのファイルがあれば同じく作り直す(fork 独自のページの行が上流の生成結果に無いため)。5d の許可集合の内側の変更になる。
   d. **区間外変更の検査**(必須。c と移植の後、merge コミットの前。読み取りのみ):
      - 許可集合 = `git diff --name-only $(git merge-base <pre> <区間の merge 先>) <区間の merge 先>` + 区間の `moved:` の移動先(ディレクトリならその配下)。
      - 実際の変更 = `git diff --name-only <pre>`(ステージ済み・未ステージの両方)。
      - 両方を一時ファイルに書いて `comm -13` で突き合わせ、許可集合の外が 1 件でもあれば停止条件として `git merge --abort` し、その一覧を根拠に示す。
      - fast-forward になった場合は merge の推定が働かないので検査は不要。
   e. 通れば `git commit --no-edit` で merge コミットを作る。merge 後にツリーの notice を再走査し、区間の想定と食い違えば報告して止める。
6. **実行**: その区間の計画の順に実施。
   - 通常ステップ: Claude が実行(コード修正、`pnpm dc:generate` 等のコマンド、バックフィル task、データ移行)。
   - 掃討と追従: 計画に載せた fork 固有コード(notice の掃討と「上流の変更点の洗い出し」の両方)を同じ区間で新しい使い方へ揃え、「上流が持つパスでの fork の編集の見直し」で a にしたものを fork の持ち物の場所へ移す。旧 API の呼び出し・互換 shim や旧名・旧パスへの依存・不要になった独自実装を残さない。merge の後に洗い出しをやり直して見つかった分も同じ区間で揃える。揃え方に fork 固有の判断が要るものは停止条件として止める(ユーザーが「残す」と決めたら、残した箇所と理由を台帳の `notes:` に書く)。notice の無い追従、notice に目印が無く掃討しきれなかったものは「上流への所見」(b) に出す。
   - **区間の検査**(notice の有無を問わず、merge だけの区間も含めて毎区間、commit の前に必ず): `pnpm typecheck`(全体)と、区間で変わったファイル(merge と追従で変わった `.ts` / `.tsx` / `.js` / `.mjs`)に絞った `pnpm exec eslint <files>`。落ちたら、その区間の追従として直してから commit する(修正元の区間で、修正が控えている箇所の失敗は直さない: 上記「修正(fixes)」)。区間の前から fork にあった指摘は区間の失敗にしない(必要なら merge 前の HEAD で同じ検査をして比べる)。ただし、そのうち上流の持ち物(CLAUDE.md の CORE_FILES・祖先リポの lib)のファイルにあるものは「上流への所見」(a) に出す(どのファイルの何件か + 検査の出力。全 fork が受け継いでいる可能性が高い)。直し方が自明でなければ停止条件。
   - `[user-run]` ステップ: 「プロンプトに `! <コマンド>` と打ってください」と依頼して待つ。`!` プレフィックスはセッション内実行で出力が会話に流れ込むので、**出力を確認し、成功を判定してから**後続を再開する。失敗していたら取り繕わず対処を提示する。
   - notice の `verify:` を自分で実行して確認する。`moved:` を移植した区間は新しいパス側の確認も行う(→ moved.md 手順 5)。
   - 下流を持つ fork なら、verify の後に中継判定を行う(→ relay.md「中継判定」。中継が必要なら中継 notice の下書きまでこの区間で作る)。
   - 型チェックは `pnpm typecheck` で行う。古い notice の `verify:` が `tsc --noEmit` と書いていても `pnpm typecheck` に読み替える(`tsc --noEmit` は dev サーバーが残した古い `.next/**/validator.ts` で TS2307 を出すため。`.notices/README.md` 参照)。
   - `pnpm typecheck` が**自 fork では使っていない上流の `_screen/*` 既定 Screen**(page.tsx を `_components/` に向けているルート等)で落ちたら、原因は自 fork の core 編集の非互換(必須 props の追加・使わない core コードの削除など)。直すのは core 側(足した props を省略可能+空の既定値に戻す、消したものを上流から戻す)で、上流の Screen は編集しない(CLAUDE.md CORE_FILES `fork_core_edit_compat`、`src/lib/screens/README.md` §7)。台帳の notes に何を戻したかを書く。
7. **記録とコミット**(途中確認なしで連続実行):
   a. 自 fork 台帳 `.notices/applied/<fork-id>.md` に追記(無ければヘッダごと作成。英語):
      ```
      # APPLIED LEDGER fork:<own origin url>
      - id:<notice id> | date:<ISO8601> | commit:<short sha or -> | relay:<none | relay notice id> | notes:<deviations from required_actions, or ->
      ```
      `relay:` 欄は下流を持つ fork だけが書き、末端 fork は欄ごと省く。covers 側 notice を記録したときの covered id の行・`relay:` の値 → relay.md「台帳への追加」。
   b. 差分(適用実装+台帳+この区間で下書きした中継 notice)をコミット & プッシュ。メッセージ: 1行サマリ + 空行 + `downstream-notice: <id>`(区間内の全 id、1 行ずつ)+ 環境指定の Co-Authored-By トレーラー。ブランチ運用は自リポの方針に従う。push できない場合は取り繕わず報告し、台帳の `notes:` に正直に反映する。
   c. その区間の merge コミットも未 push なら一緒に push する。
8. **報告**(日本語。区間の終わりで止まるたび・最終報告の両方):
   - その区間: merge 結果(取り込みコミット数)/ 適用した notice と verify 結果 / 区間の検査(typecheck・lint)の結果 / コミット sha / 既知の未修正の行(上記「修正(fixes)」の報告。当たるときだけ)。下流を持つ fork なら中継判定の報告行(→ relay.md)。
   - 揃えたもの・残したものを、次の決まった行で書く(鍵は英語のまま。fleet などが読んで写す):
     ```
     aligned: <この区間で新しい上流の仕組みに作り直した fork のコード: 何を → どう(件数)。上流が持つパスから移したものも | none>
     kept_old: <古い使い方のまま残したもの・上流が持つパスに残した fork の編集: 箇所 — 理由(b は /order <上流リポ> 文案あり)>
     ```
     `aligned:` は毎回書く(無ければ `none`)。`kept_old:` は何かを残したときだけ書く。
   - **引き継ぎ**(区間の終わりで止まるたび必ず。この節だけで次の区間に入れる内容にし、前の区間の経緯は書かない): ここまでの区間ごとの sha(`S<i> <checkpoint> <sha> pushed|push held`)/ このセッションで人間が下した判断(残した旧使い方・スキップした notice・条件付きの go)/ 次の merge 先(短 sha と checkpoint)/ 残っている作業(未消化の `manual_steps`・保留中の所見・未 push)。
   - 止まるときは次の区間の詳細計画と、残りの区間の概観(1 行ずつ)を添える。
   - `manual_steps` があれば**まとめてチェックリストとして提示**(ここだけは人間の宿題)。
   - 最後に「**上流への所見**」(上記、無ければ「なし」)。停止条件で止まった場合も同じ構成で、止まった区間と理由・選択肢を先頭に置く。

## エッジケース
(中継に関するもの → relay.md、`moved:` に関するもの → moved.md)
- 上流に `.notices/` が無い(この仕組み導入前の上流): 通常の merge として完走し、その旨だけ報告。
- notice のスキーマが読めない/欠損: その notice はスキップして報告に含める(黙殺しない)。
- 台帳にあるがツリーに無い id(上流が done/ へ移動済み): 正常。何もしない。
- checkpoint notice の追加 commit が既に HEAD の祖先(merge 済み)なのに台帳に無い: ツリー内の未適用として区間 0 で扱う(merge 不要)。
- 流入予定 notice に `checkpoint:` 欄が無い(旧スキーマ): 区切り扱い(安全側。`-` とみなしてはいけない)。
- 区間の merge 先が `<upstream>/<branch>` の祖先でない(上流が履歴を書き換えた等): その旨を報告して止める。勝手に全量 merge へ倒さない。

## 対話ルール
- ユーザーとの会話は日本語。台帳・notice への追記は英語。
- **AskUserQuestion(選択肢ウィジェット)は使わない**。計画の承認、merge 方針、コンフリクトの判断、停止時の選択肢など、ユーザーに聞くことはすべて**平文で**書いて次のメッセージを待つ。理由: このスキルは fleet(複数 fork 並列実行)では統括が tmux 経由で平文を送り込んで回答するため、ウィジェットだと回答できない。単体実行でも同じ挙動にし、聞き方を一本化する。
