これは調査の進め方のメモです。モードの切り替えではありません。ここまでの会話の文脈・方針・口調・制約はそのまま維持し、以下は骨子として扱ってください。調査テーマが明示されていなければ、会話の流れから自然に決めます: $ARGUMENTS

## 考え方

委譲(サブエージェント)は「広く浅く」に強く、細部と正確さに弱い。自分で読むのは「狭く深く」に強く、コンテキストを消費する。両者を二段に分けると、弱点が互いに打ち消される。

## 一段目: 広く浅く(委譲)

- 調査テーマを独立した軸に分ける(例: 書き込み経路 / 読み取り経路 / 設定 / テスト / ドキュメント)。1軸1エージェント、独立なら並列に起動する。軸分けの参考: CLAUDE.md の CODE_PLACEMENT と ARCHITECTURE の層。
- 原則フレッシュ型の読み取り専用エージェント(Explore)を使う。会話の文脈そのものが前提になる軸だけフォーク型にする。
- プロンプトには必ず含める: 目的 / 既に分かっていること / 探索範囲 / 除外対象(generated ファイルなど) / 網羅性の指示 / 報告形式。
- 網羅性の指示は明示する: 「該当しそうな箇所は確度が低くても全部列挙する。件数の上限は設けない。確度を high / medium / low で付ける」。
- 報告形式: 1件につき「パス:行 | 一行要旨 | 確度 | 読むべき理由」。コードの引用は最小限でよい。
- 候補が数十件を超える軸は、全件ではなく件数と分類を報告させ、絞り込み方針を決めてから再投入する。

## 統合

報告を重複除去し「必読 / 候補 / 除外」に仕分ける。除外は理由を残す。一段目の取りこぼしは二段目で固定されるので、仕分けは広めに取る。

## 二段目: 狭く深く(自分で読む)

- 必読を自分で読む。読んで新しい参照先が出たら追う。
- 違和感があれば、その軸だけ再調査する。同じエージェントに SendMessage で追加質問する方が、新規起動より文脈が保たれる。

## 報告

ファイルの地図、影響範囲、未確定事項、次の提案をまとめて止まる。調査の結果として実装に進むかどうかは、ここまでの会話の約束に従う(通常は承認を待つ)。

## 守ること

- 調査中はファイルを編集しない。
- dev サーバーを起動しない。
