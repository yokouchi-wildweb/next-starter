# messaging Internals（連絡の形と、なぜそうなっているか）

## Overview

連絡の受け持ちの全体の形と、その背景（なぜそうしたか・採らなかった案と理由）を部品ごとにまとめる（D116）。使い方は [README.md](README.md)、各部品の細部は各フォルダの README。決定の番号（D109〜D132）は評議会 system-messaging-templates の記録。

全体の形を一言でいうと: **連絡 = カテゴリー + レイアウト + 欄の中身**。定義連絡（自動で送る）も管理者のテンプレート（手で送る）も同じ形で、送信チャンネル（メール・お知らせ・LINE・fork の送信チャンネル）はカテゴリーだけが持ち、見た目はレイアウトが全送信チャンネルの分を持つ。

## Internals

### レイアウト（layouts/<名前>/）

形:

- 1 つのフォルダ = 1 つのレイアウト。`layout.ts`（`defineMessageLayout`: 欄の宣言・欄ごとの仮の文 `placeholder`・要約 `summary`・管理者が選べる印 `adminSelectable`・版 `version` と改版の対応 `revisions`）+ 送信チャンネルごとの描き方（任意: `email.tsx` = server、`inApp.tsx` = client）
- 1 つのレイアウトで全送信チャンネル。送信チャンネルだけの欄は欄の宣言の `channels` に送信チャンネルの鍵を持つ（例 statement の `shortBody` はお知らせと LINE だけ）。レイアウトは種別・カテゴリー・送信チャンネルの一覧を知らない
- 欄の型は lib の語彙で固定（1行テキスト・段落・複数行テキスト・画像・ボタン・リンク・日付・数・選択肢・並び・組・ラベルと値・ブロックの並び）。ブロックの並びの欄は `{ allow, min, max }`（小見出し・段落・ボタン・画像・区切り・ラベルと値・箇条書き）
- 見た目の差し替え: 送信チャンネルごとの描き方は 1 行スイッチ（`NoticeEmail.tsx` → `.default.tsx`、fork は `.replace.tsx`）。全メールの枠（ロゴ・色・末尾）は lib/mail の `MailFrame` のスイッチで一度に替える
- 生成の一覧は 3 つ: レイアウト（`extensions/messagingLayouts.ts`）・メールの描き方（server、`layoutEmails`）・お知らせの描き方（client、`layoutInApps`）
- 改版: 欄の鍵を変える時は `version` を上げ、`revisions[前の版]` に「前の欄の鍵 → 新しい鍵か null（捨てる）」を書く。保存した中身（テンプレートの版・テキストの編集・送信の中身）は読む時に `upgradeLayoutValues` で今の版へ読み替え、読めなければ止める

背景:

- **送信チャンネルごとに別のレイアウトにしない**: 管理者が送信チャンネルの数だけ文を書くことになり、fork が送信チャンネル（プッシュ・SMS）を足すたびに全部のレイアウトへ書き足す羽目になる。1 つのレイアウトが全送信チャンネルを持ち、描き方の無い送信チャンネルは下の 3 段で描けるようにした（D122、r11.2 で B・C が出した案を退けた）
- **前の形（送信チャンネルが欄を決める）をやめた**: 送信チャンネルごとの欄（メールの件名・段落・ボタン、お知らせの題・本文…）と連絡ごとの view があり、同じ文を送信チャンネルごとに書き、管理画面の入力も送信チャンネルごとだった。欄をレイアウトの側へ移し、送信チャンネルは「形式と送り方」だけにした（r11 の一致）
- **欄の型を lib で固定**: 型は入力の部品・zod・記録・要約・プレビューの 5 か所が読むので、レイアウトごとに自由な型を許すと 5 か所が追いつかない（D123、前例は domain の fieldTypes の表）。fork は入力の部品を自分のドメインか lib の `plugs/formInputs/` に登録するだけ
- **client と server の描き方の一覧を分ける**: メールの描き方は server、お知らせの描き方は client の部品。1 つの一覧に混ぜると client に server の部品が入る（D122、r11 の T）

### 描き方の 3 段

形: 送信チャンネルごとに「レイアウトのその送信チャンネルの描き方 > 送信チャンネルの汎用の描き方（欄の型とブロックを宣言の順に描く）> 要約から」の順で最初に描けた物で描く（lib/messaging `resolveRendering` / `buildChannelContent`、送る口の 1 か所 `services/server/sendMessage/content.ts`）。どれでも描けない送信チャンネルは送る前・テンプレートの保存・プレビューで止める。要約 = 題・本文・画像・行き先 + 任意の短い本文（プッシュ・LINE・お知らせの一覧）。

背景: 送信チャンネルを足してもレイアウトに書き足さずに済み、要約は最後の拠り所に留まる（D124）。送信チャンネルは「要約から描ける」を宣言するだけで、どのレイアウトの連絡も届けられる。

### 連絡定義（plugs/messages/<名前>.ts）

形: `defineMessage({ key, label, category, vars, layout, values, required?, record?, throttle?, adminEditableOnly? })`。`values` はレイアウトの欄の中身で、文字の中に `{{鍵}}` を書ける（vars・共通の埋め込み情報・当たる enrichers の値）。送信チャンネルは書かない（カテゴリーから引く）。fork は `<名前>.override.ts` で `values`（欄ごと）・`label`・`enabled` などを重ねる。

背景:

- **自動（コード）と手動（テンプレート）を同じ形に**: どちらも「カテゴリー + レイアウト + 欄の中身」で、送る口・送信の記録・プレビューが 1 つで済む（D125）
- **送信チャンネルはカテゴリーだけが持つ**: 配信停止の単位はカテゴリー × 送信チャンネルなので、送信チャンネルが連絡や送信ごとに変わると好みのページの表が嘘になる（README「運用で間違えやすい線」）
- **既定の文言を DB のシードにしない**: 上流・中間の Tier の直しが届かず、上書きと二重になり、DB が未設定の時に壊れる（D21 のまま、ボスの案を 4 席が退けた）。コードの値が正本で、管理画面の値は上に重ねるだけ

### テンプレートと自由連絡

形:

- DB のテンプレート（`message_templates` / `message_template_versions`）= カテゴリー + レイアウト + 欄の中身 + 専用の埋め込み情報の宣言。公開すると版になり、送信は送る時の版を固定する（services/server/templates/README.md）
- 自由連絡 = カテゴリー + レイアウト（管理画面で選べる `adminSelectable` の物だけ）+ 欄の中身、か DB のテンプレートの版 + 欄の中身。管理の送る画面も fork のコードからの管理の送信（`sendFreeMessage`）も同じ口（services/server/sendMessage/README.md）
- 作る・送る画面の順番 = 種別 →（カテゴリー: その種別に 2 つ以上ある時だけ）→ レイアウト（管理者が選べる物）→ 中身。送る画面は種別の次に宛先（種別が許す宛先だけ、direct はグループも）
- レイアウトを替えると中身は消える（確認を出す）。保存した新しい版は新しいレイアウトの中身だけを持ち、前の版は前のレイアウトのまま履歴に残る
- 送る画面で読み込んだ文面は直せる。直してもテンプレートとのつながり（テンプレートと版）は残り、送信に直した印が付く。切るのは『テンプレートの読み込みを解除』だけ。直した文をテンプレートに戻すのは『テンプレートを更新』（送るのとは別の操作）

背景:

- **種別を先に選ぶ**: 何のための送信か（告知・個別・宣伝）を運用者が先に自分で決めれば、システムは種別に合う宛先とテンプレートを出すだけでよい。選び間違いへの手当ては上流でしない（D110・D115）
- **管理者はカテゴリーを作らない**: カテゴリーは配信停止の単位で、利用者の好みのページの行になる。コード（点 `messagingCategories/`）で足し、3 種別ともどれも同じ仕組みで足せる（上流は種別ごとに 1 つ）。カテゴリーを足す理由のうち、レイアウト・テンプレート・既定のカテゴリーの送信チャンネルの上書き・送る時の送信チャンネルのオフの 4 つで置き換えられないのはプロモーションの止める単位だけだった（D115）
- **システムテンプレートを廃止した**（D171・D201）: 前は自由連絡を『白紙のシステムテンプレートを選んで送る』に揃えていた（D117）が、定義連絡と自由連絡の取り違えを防ぐためやめ、自由連絡はレイアウトを直に選ぶ。前の管理用の連絡定義 3 本（adminAnnouncement・adminDirect・adminPromotion）も持たない
- **レイアウトどうしの中身の付け替えをしない**: 組み合わせごとの対応を持つより一から入れ直す方が単純（D113）
- **直してもつながりを残す**: 切るかどうかは修正の中身を見た管理者が決める。うっかり文を崩さず、直す時は能動的に意思表示する（D118〜D120）

### 埋め込み情報（文面の {{名前}}）

形（lib/messaging `vars/`、src/lib/messaging/README.md「埋め込み情報」）:

- 共通の埋め込み情報 = どの連絡・テンプレートにも書ける。共通の文脈（`MESSAGE_COMMON_VARS`: 受信者名・受信者のメール・サービス名・サイトのURL、間引きのある連絡だけまとめた件数）と、当たる enrichers の provides。値は送る口が受信者ごとに埋める
- 専用の埋め込み情報 = テンプレートごとに管理者が宣言する（型 1行テキスト・数・日付・日時・URL・選択肢、必須・既定値）。値は送る人が送る時に入れ、送信の `vars` に残る（定義連絡の vars と同じ 1 つの列、D202）
- 名前は英語の鍵と日本語の別名の 2 つ。文面にはどちらでも書け（`{{開始日時}}` = `{{startAt}}`）、別名は専用どうしも共通とも重ならない（保存と送る前に `checkVarCatalog` が止める）。画面の語は『変数』でなく『埋め込み情報』、タグは別名でコピーする

背景:

- **2 種類に分ける**: 変数の存在意義は「受信者ごとに埋まる物」と「その送信で送る人が決める物」の 2 つしかない（D111）。テンプレートの受信者ごとの変数（`source: recipient`）は値を渡す口が無く壊れていたのでやめた（D126）
- **日本語の別名**: 管理者に英語の鍵を読ませない（D111・D112）。別名の重なりを許すと同じ `{{名前}}` が 2 つの値を指すので保存で止める
- **専用の別名は送信に残す前に鍵へ書き換える**: cron の組み直しが宣言を引き直さずに描けるように（`canonicalVarNames`）

### テキストの編集（管理画面、services/server/overrides/）

形: 定義連絡のレイアウトの欄を、管理者が欄の鍵ごとに直す（`message_overrides`）。既定で全部の欄（カテゴリーの送信チャンネルで使う分）を直せ、連絡の `adminEditableOnly` は絞るためだけ。functional（認証の連絡）・required は直せない。重なる順 = テキストの編集 > fork の上書き > 上流の既定。レイアウトの改版の対応はテキストの編集の行にも効く。

背景:

- **テンプレートと別の表**: テキストの編集は定義連絡の鍵 + 欄の道に付き、テンプレートは管理者の持ち物。混ぜると「定義連絡を直した」のか「別の連絡を作った」のかが分からなくなる（D132）
- **既定で全欄**: ボスがギルドで決め出荷済みの形に揃えた。「印を付けた欄だけ」（D129）は取り違えで、D132 が置き換えた
- **改版の対応をテキストの編集にも効かせる**: fork の DB のテキストの編集の行を手で直さずに済む（D129・D132）

### 送信の記録と組み直し

形: 送信（`message_dispatches`）は出どころ（定義連絡の鍵 / DB のテンプレートの id と版。どちらでもない = 自由連絡のレイアウト）・直した印・カテゴリー・種別・レイアウトの鍵と版・欄の中身（差し込む前）・vars・専用の埋め込み情報の値を残す。予約・cron の後回し・失敗の再送・同じ内容で送るは送信に残した物だけで描く（`resolvedOfDispatch`、定義・テンプレートを引き直さない）。描かない振る舞い（間引き・required・秘密の印）はコードの定義から読む。

背景: 送った後に定義・テンプレート・テキストの編集を直しても、予約や後回しの送信の中身が変わらないように（D128）。レイアウトの版は改版の対応で読める範囲だけで、読めなければ送らずに止める。

### 秘密と記録の段

形: 秘密の印（`secretVar`）のある値を差し込む連絡と required の連絡は本文をどこにも残さない（送信の vars・欄の中身・描いた結果・配達の本文・誤りの文）。予約・全員宛て・大きな送信にできず（400）、要求の中で送り切る。記録の段（meta / vars / full、既定は種別の性質）は送信の中身・お知らせの行にも効く（`recordPolicyOf`）。お知らせの行は秘密の値を空の字で差し込む。

背景: 秘密は記録に残さない（D33）と「後から描き直す」がぶつかるので、秘密を含む連絡は描き直しの道（予約・掃き出し）に乗せない（D128）。

### お知らせ（受け取り箱）の行

形: 行（`message_inbox_items`）= 要約の列（題・本文 = 短い本文か本文・画像・行き先）+ レイアウトの鍵・版・お知らせの欄の中身。一覧・未読のモーダルは要約、詳細（`GET /api/me/messaging/inbox/[id]`）はレイアウト・欄の中身・お知らせの欄の宣言を返し、画面が 3 段（レイアウトのお知らせの描き方 > 汎用 > 要約のカード）で描く。管理画面のお知らせのプレビューと同じ部品。記録の段が meta・秘密の連絡の行と前の形の行は要約のカード。

背景:

- **要約だけにしない**: お知らせの既定を要約だけにする案（r11.4 の B・C・T）は、管理画面のプレビューと利用者に届く形が食い違うので退け、ボタン 2 つ・表などもお知らせで描けるようにした（D121）。新しい画面は足さず、今ある詳細の改良に留めた（D91 との線）
- **要約の列も残す**: 一覧・鈴・未読のモーダルは軽い要約で足り、欄を持たない行（記録の段・前の形）も要約で描ける（D130）
- **全員宛ては共有の 1 行**: 受信者ごとに展開すると年千万行と日次 cron の遅れになる（D39）

### enrichers の当て先

形: enricher（点 `messagingEnrichers/`）は当て先 `target`（連絡の鍵 / カテゴリー / 種別 / 全部）で選ばれ、provides の値と日本語の別名（`aliases`）を足す（`enricherTargets`）。上流の `displayName` は管理の 3 種別に当てる。

背景: 前の当て先（連絡の鍵か全部）は管理用の定義 3 本に当てていたので、それをやめると当て先が無くなる。カテゴリー・種別でも当てられるようにした（D127）。
