# messaging Internals（連絡の形と、なぜそうなっているか）

## Overview

連絡の受け持ちの全体の形と、その背景（なぜそうしたか・採らなかった案と理由）を部品ごとにまとめる（D116）。使い方は [README.md](README.md)、各部品の細部は各フォルダの README。決定の番号（D109〜D132）は評議会 system-messaging-templates の記録。

全体の形を一言でいうと: **連絡 = カテゴリー + ひな形 + 欄の中身**。コードの連絡（自動で送る）も管理者のテンプレート（手で送る）も同じ形で、経路（メール・お知らせ・LINE・fork の経路）はカテゴリーだけが持ち、見た目はひな形が全経路の分を持つ。

## Internals

### ひな形（layouts/<名前>/）

形:

- 1 つのフォルダ = 1 つのひな形。`layout.ts`（`defineMessageLayout`: 欄の宣言・欄ごとの仮の文 `placeholder`・要約 `summary`・管理者が選べる印 `adminSelectable`・版 `version` と改版の対応 `revisions`）+ 経路ごとの描き方（任意: `email.tsx` = server、`inApp.tsx` = client）
- 1 つのひな形で全経路。経路だけの欄は欄の宣言の `channels` に経路の鍵を持つ（例 statement の `shortBody` はお知らせと LINE だけ）。ひな形は種別・カテゴリー・経路の一覧を知らない
- 欄の型は lib の語彙で固定（1 行の文・段落・長い文・画像・ボタン・リンク・日付・数・選択肢・並び・組・項目と値・ブロックの並び）。ブロックの並びの欄は `{ allow, min, max }`（小見出し・段落・ボタン・画像・区切り・項目と値の表・箇条書き）
- 見た目の差し替え: 経路ごとの描き方は 1 行スイッチ（`NoticeEmail.tsx` → `.default.tsx`、fork は `.replace.tsx`）。全メールの枠（ロゴ・色・末尾）は lib/mail の `MailFrame` のスイッチで一度に替える
- 生成の一覧は 3 つ: ひな形（`extensions/layouts.ts`）・メールの描き方（server、`layoutEmails`）・お知らせの描き方（client、`layoutInApps`）
- 改版: 欄の鍵を変える時は `version` を上げ、`revisions[前の版]` に「前の欄の鍵 → 新しい鍵か null（捨てる）」を書く。保存した中身（テンプレートの版・文言の上書き・回の中身）は読む時に `upgradeLayoutValues` で今の版へ読み替え、読めなければ止める

背景:

- **経路ごとに別のひな形にしない**: 管理者が経路の数だけ文を書くことになり、fork が経路（プッシュ・SMS）を足すたびに全部のひな形へ書き足す羽目になる。1 つのひな形が全経路を持ち、描き方の無い経路は下の 3 段で描けるようにした（D122、r11.2 で B・C が出した案を退けた）
- **前の形（経路が欄を決める）をやめた**: 経路ごとの欄（メールの件名・段落・ボタン、お知らせの題・本文…）と連絡ごとの view があり、同じ文を経路ごとに書き、管理画面の入力も経路ごとだった。欄をひな形の側へ移し、経路は「形式と送り方」だけにした（r11 の一致）
- **欄の型を lib で固定**: 型は入力の部品・zod・記録・要約・プレビューの 5 か所が読むので、ひな形ごとに自由な型を許すと 5 か所が追いつかない（D123、前例は domain の fieldTypes の表）。fork は入力の部品を `wiring/formInputs` に登録するだけ
- **client と server の描き方の一覧を分ける**: メールの描き方は server、お知らせの描き方は client の部品。1 つの一覧に混ぜると client に server の部品が入る（D122、r11 の T）

### 描き方の 3 段

形: 経路ごとに「ひな形のその経路の描き方 > 経路の汎用の描き方（欄の型とブロックを宣言の順に描く）> 要約から」の順で最初に描けた物で描く（lib/messaging `resolveRendering` / `buildChannelContent`、送る口の 1 か所 `services/server/sendMessage/content.ts`）。どれでも描けない経路は送る前・テンプレートの保存・プレビューで止める。要約 = 題・本文・画像・行き先 + 任意の短い本文（プッシュ・LINE・お知らせの一覧）。

背景: 経路を足してもひな形に書き足さずに済み、要約は最後の拠り所に留まる（D124）。経路は「要約から描ける」を宣言するだけで、どのひな形の連絡も届けられる。

### 連絡の定義（messages/<名前>.ts）

形: `defineMessage({ key, label, category, vars, layout, values, required?, record?, throttle?, adminEditableOnly? })`。`values` はひな形の欄の中身で、文字の中に `{{鍵}}` を書ける（vars・共通の埋め込み情報・当たる enrichers の値）。経路は書かない（カテゴリーから引く）。fork は `<名前>.override.ts` で `values`（欄ごと）・`label`・`enabled` などを重ねる。

背景:

- **自動（コード）と手動（テンプレート）を同じ形に**: どちらも「カテゴリー + ひな形 + 欄の中身」で、送る口・回の記録・プレビューが 1 つで済む（D125）
- **経路はカテゴリーだけが持つ**: 配信停止の単位は種類 × 経路なので、経路が連絡や回ごとに変わると好みのページの表が嘘になる（README「運用で間違えやすい線」）
- **既定の文言を DB のシードにしない**: 上流・中間の Tier の直しが届かず、上書きと二重になり、DB が未設定の時に壊れる（D21 のまま、ボスの案を 4 席が退けた）。コードの値が正本で、管理画面の値は上に重ねるだけ

### テンプレートとシステムテンプレート

形:

- DB のテンプレート（`message_templates` / `message_template_versions`）= カテゴリー + ひな形 + 欄の中身 + 専用の埋め込み情報の宣言。公開すると版になり、回は送る時の版を固定する（services/server/templates/README.md）
- システムテンプレート（受け口 `templates/<名前>.ts`）= コードで宣言する白紙とできあがった文面（上流は種別ごとにシンプル・リッチの白紙 + メンテナンスのお知らせ、D119。専用の埋め込み情報も持てる）。管理画面で直せない・消せない、DB のテンプレートと 1 つの一覧に印つきで並ぶ。その場で書く送信も fork のコードからの管理の送信（`sendTemplateMessage`）もこの白紙から書く
- 作る・送る画面の順番 = 種別 →（カテゴリー: その種別に 2 つ以上ある時だけ）→ ひな形（管理者が選べる物）→ 中身。送る画面は種別の次に宛先（種別が許す宛先だけ、direct はグループも）
- ひな形を替えると中身は消える（確認を出す）。保存した新しい版は新しいひな形の中身だけを持ち、前の版は前のひな形のまま履歴に残る
- 送る画面で読み込んだ文面は直せる。直してもテンプレートとのつながり（テンプレートと版）は残り、回に直した印が付く。切るのは『テンプレートの読み込みを解除』だけ。直した文をテンプレートに戻すのは『テンプレートを更新』（送るのとは別の操作）

背景:

- **種別を先に選ぶ**: 何のための送信か（告知・個別・宣伝）を運用者が先に自分で決めれば、システムは種別に合う宛先とテンプレートを出すだけでよい。選び間違いへの手当ては上流でしない（D110・D115）
- **管理者はカテゴリーを作らない**: カテゴリーは配信停止の単位で、利用者の好みのページの行になる。コード（受け口 `categories/`）で足し、3 種別ともどれも同じ仕組みで足せる（上流は種別ごとに 1 つ）。カテゴリーを足す理由のうち、ひな形・テンプレート・既定のカテゴリーの経路の上書き・送る時の経路のオフの 4 つで置き換えられないのはプロモーションの止める単位だけだった（D115）
- **白紙のシステムテンプレートを置く**: カテゴリーから直に送る案（r11.4 の A）もあったが、その場の送信・テンプレートの送信・fork のコードからの送信を『テンプレートを選んで送る』1 つの手順に揃えるため白紙を置いた（D117）。前の管理用の連絡の定義 3 本（adminAnnouncement・adminDirect・adminPromotion）はこれに替えてやめた
- **ひな形どうしの中身の付け替えをしない**: 組み合わせごとの対応を持つより一から入れ直す方が単純（D113）
- **直してもつながりを残す**: 切るかどうかは修正の中身を見た管理者が決める。うっかり文を崩さず、直す時は能動的に意思表示する（D118〜D120）

### 埋め込み情報（文面の {{名前}}）

形（lib/messaging `embedded/`、src/lib/messaging/README.md「埋め込み情報」）:

- 共通の埋め込み情報 = どの連絡・テンプレートにも書ける。共通の文脈（`MESSAGE_COMMON_EMBEDDED`: 受信者名・受信者のメール・サービス名・サイトのURL、間引きのある連絡だけまとめた件数）と、当たる enrichers の provides。値は送る口が受信者ごとに埋める
- 専用の埋め込み情報 = テンプレートごとに管理者が宣言する（型 1 行の文・数・日付・日時・URL・選択肢、必須・既定値）。値は送る人が送る時に入れ、回の `embedded_values` に残る
- 名前は英語の鍵と日本語の別名の 2 つ。文面にはどちらでも書け（`{{開始日時}}` = `{{startAt}}`）、別名は専用どうしも共通とも重ならない（保存と送る前に `checkEmbeddedCatalog` が止める）。画面の語は『変数』でなく『埋め込み情報』、タグは別名でコピーする

背景:

- **2 種類に分ける**: 変数の存在意義は「受信者ごとに埋まる物」と「その回に送る人が決める物」の 2 つしかない（D111）。テンプレートの受信者ごとの変数（`source: recipient`）は値を渡す口が無く壊れていたのでやめた（D126）
- **日本語の別名**: 管理者に英語の鍵を読ませない（D111・D112）。別名の重なりを許すと同じ `{{名前}}` が 2 つの値を指すので保存で止める
- **専用の別名は回に残す前に鍵へ書き換える**: cron の組み直しが宣言を引き直さずに描けるように（`canonicalEmbeddedNames`）

### 文言の上書き（管理画面、services/server/overrides/）

形: コードの連絡のひな形の欄を、管理者が欄の鍵ごとに直す（`message_overrides`）。既定で全部の欄（カテゴリーの経路で使う分）を直せ、連絡の `adminEditableOnly` は絞るためだけ。functional（認証の連絡）・required は直せない。重なる順 = 管理画面の値 > fork の上書き > 上流の既定。ひな形の改版の対応は上書きの行にも効く。

背景:

- **テンプレートと別の表**: 上書きはコードの連絡の鍵 + 欄の道に付き、テンプレートは管理者の持ち物。混ぜると「コードの連絡を直した」のか「別の連絡を作った」のかが分からなくなる（D132）
- **既定で全欄**: ボスがギルドで決め出荷済みの形に揃えた。「印を付けた欄だけ」（D129）は取り違えで、D132 が置き換えた
- **改版の対応を上書きにも効かせる**: fork の DB の上書きの行を手で直さずに済む（D129・D132）

### 送った回の記録と組み直し

形: 回（`message_dispatches`）は出どころ（コードの連絡の鍵 / システムテンプレートの鍵 / DB のテンプレートの id と版）・直した印・カテゴリー・種別・ひな形の鍵と版・欄の中身（差し込む前）・vars・専用の埋め込み情報の値を残す。予約・cron の後回し・失敗の再送・同じ内容で送るは回に残した物だけで描く（`resolvedOfDispatch`、定義・テンプレートを引き直さない）。描かない振る舞い（間引き・required・秘密の印）はコードの定義から読む。

背景: 送った後に定義・テンプレート・上書きを直しても、予約や後回しの回の中身が変わらないように（D128）。ひな形の版は改版の対応で読める範囲だけで、読めなければ送らずに止める。

### 秘密と記録の段

形: 秘密の印（`secretVar`）のある値を差し込む連絡と required の連絡は本文をどこにも残さない（回の vars・欄の中身・描いた結果・配達の本文・誤りの文）。予約・全員宛て・大きな送信にできず（400）、要求の中で送り切る。記録の段（meta / vars / full、既定は種別の性質）は回の中身・お知らせの行にも効く（`recordPolicyOf`）。お知らせの行は秘密の値を空の字で差し込む。

背景: 秘密は記録に残さない（D33）と「後から描き直す」がぶつかるので、秘密を含む連絡は描き直しの道（予約・掃き出し）に乗せない（D128）。

### お知らせ（受け取り箱）の行

形: 行（`message_inbox_items`）= 要約の列（題・本文 = 短い本文か本文・画像・行き先）+ ひな形の鍵・版・お知らせの欄の中身。一覧・未読のモーダルは要約、詳細（`GET /api/me/messaging/inbox/[id]`）はひな形・欄の中身・お知らせの欄の宣言を返し、画面が 3 段（ひな形のお知らせの描き方 > 汎用 > 要約のカード）で描く。管理画面のお知らせのプレビューと同じ部品。記録の段が meta・秘密の連絡の行と前の形の行は要約のカード。

背景:

- **要約だけにしない**: お知らせの既定を要約だけにする案（r11.4 の B・C・T）は、管理画面のプレビューと利用者に届く形が食い違うので退け、ボタン 2 つ・表などもお知らせで描けるようにした（D121）。新しい画面は足さず、今ある詳細の改良に留めた（D91 との線）
- **要約の列も残す**: 一覧・鈴・未読のモーダルは軽い要約で足り、欄を持たない行（記録の段・前の形）も要約で描ける（D130）
- **全員宛ては共有の 1 行**: 受信者ごとに展開すると年千万行と日次 cron の遅れになる（D39）

### enrichers の当て先

形: enricher（受け口 `enrichers/`）は当て先 `target`（連絡の鍵 / カテゴリー / 種別 / 全部）で選ばれ、provides の値と日本語の別名（`aliases`）を足す（`enricherTargets`）。上流の `displayName` は管理の 3 種別に当てる。

背景: 前の当て先（連絡の鍵か全部）は管理用の定義 3 本に当てていたので、それをやめると当て先が無くなる。カテゴリー・種別でも当てられるようにした（D127）。
