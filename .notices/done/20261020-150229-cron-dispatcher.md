change: scheduled tasks are now registry-driven. src/registry/cronTaskRegistry.ts (upstream) + src/registry/forkCronTaskRegistry.ts (fork-owned, ships empty) are the single source; a dispatcher GET /api/cron/dispatch/<15m|hourly|daily|all> fans out to every registered task whose enabled() is true. vercel.json now holds only the dispatcher, generated by `pnpm cron:generate --plan hobby|pro` (hobby = one daily /api/cron/dispatch/all, Vercel Hobby compatible). New: `pnpm cron:check` (deploy:all runs it first and aborts when vercel.json lacks the dispatcher), `pnpm test:cron-wiring`, `pnpm task --cadence <c>` for non-Vercel schedulers, src/config/app/cron-schedule.config.ts (per-cadence cron expressions, UTC). All core /api/cron/<task>/route.ts became one line `createCronTaskRoute(getCronTask("<task>"))`; scheduled entries moved out of scripts/tasks/run.ts TASKS into the registry (run.ts keeps one-shots in ONE_SHOT_TASKS). vercel.json.example now lists the 3 pro dispatcher entries only. Also: CLAUDE.md DOWNSTREAM_NOTICES delete_or_move rule (deleting/moving a fork-extensible file ships its notice in the SAME commit).
why: forks copied vercel.json.example by hand and forgot tasks (production ran without audit-log-prune / audit-log-recover-dead-letter / user-login-event-prune), the example's hourly entries broke Vercel Hobby deploys, and opt-in crons made "every example cron is in vercel.json" verifies unpassable. With the dispatcher, future upstream tasks start running on merge with no fork action and no notice. A fork that keeps per-task entries next to the dispatcher would run every task twice, so the old entries must go.
