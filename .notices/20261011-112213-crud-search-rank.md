severity: info
change: Added relevance ranking to createCrudService.search / searchWithDeleted (Drizzle only): new SearchParams `searchRank?: boolean | { fields: (string | {field, weight?})[] }` puts a per-field tiered score (exact 100 > prefix 60 > word-start 40 > substring 20, × weight, summed across fields) at the head of ORDER BY; WHERE / count / result set unchanged. Service option `defaultSearchRank` (+ domain.json `searchRank` key expanded by dc:generate) declares weights; `true` falls back to searchFields equal-weight. AsyncComboboxInput / AsyncMultiSelectInput now send `searchRank: true` by default, so every picker (generated ConfiguredAsyncRelationField, hand-wrapped UserAsyncCombobox/PrizeItemAsyncCombobox-style wrappers whose searchFn spreads params, direct usages) is ranked with zero config. Admin lists / non-picker search calls keep their ordering. Legacy searchPriorityFields / prioritizeSearchHits still work (@deprecated). SQL helpers buildSearchWhere / buildSearchRankOrderBy / buildSearchPriorityOrderBy exported from @/lib/crud/drizzle. GET /api/[domain]/search and /api/profile/[role]/search parse `searchRank` fail-closed (bool or JSON spec, unknown keys / weight outside 0<w<=100 / >20 fields → 400). Purely additive; no DB migration.
why: Admin user pickers searched name+email with `%q%` ILIKE OR ordered by createdAt DESC only, so a 2-char query like "ab" buried the intended user (name starts with "ab") under hundreds of email-domain substring hits. The old priority machinery was never wired from pickers. Fix lives in the shared search + shared picker so all domains benefit; downstream wrappers that re-implement the CASE priority can drop that code.
