checkpoint: admin-relation-options-prefetch
change: (1) The dc:generate admin Create/Edit screens' relation prefetch now actually works and is limited to relations the form fetches. New shared loader `loadAdminRelationOptions(domainConfig)` (src/features/core/admin/services/server/loaders/adminRelationOptions.ts) reads ONLY "static" relations (belongsTo + front-side belongsToMany whose formInput is anything but asyncCombobox/asyncMultiSelect/custom — the default select/checkbox included; NOT `includeRelationTable:false` inverse belongsToMany, NOT hasMany/hasOne), resolves each service from `serviceRegistry` by the relation's domain name (same path as `GET /api/<domain>`), and returns `{ [swrKey]: { [domain]: rows } }` keyed exactly like `useRelationOptions`'s `useSWR` key (`relationOptions:<domain,...>`, now a string key). The generator (scripts/domain-config/generator/admin-routes/helpers.mjs) emits `const relationFallback = await loadAdminRelationOptions(domainConfig)` + `<SWRConfig value={{ fallback: relationFallback }}>` only when at least one static relation exists, and no per-relation service imports anymore. The judgment "which relations are form relations / which are fetched" lives in ONE file, `src/lib/domain/relations/relationOptions.mjs` (`getFormRelations` / `getStaticRelations` / `relationOptionsKey`), imported by `useRelationOptions`, the loader, and both generators (admin-routes + components/utils/fields.mjs). `loadAdminRelationLists` is DEPRECATED (kept this checkpoint, deleted at the next one). (2) `loadAdminListScreen(service, props, options?)` gained an optional third argument `AdminListSearchOptions` = `withRelations` / `hasManyLimit` / `orderBy` / `where` / `relationWhere` (JSON-able only; `extraWhere` is not accepted — write a `_components/loader.ts` for that). Two-arg calls are unchanged. New test `pnpm test:relation-options`.
why: oripa-do (upstream-request 20261018-175856) found the generator prefetching every relation (async inputs, inverse belongsToMany) and no typed way to pass `withRelations` to the list loader. Investigation showed the prefetch was worse than wasteful: its fallback keys (`sampleCategories`, the `use<Domain>List` keys) never matched the form's `useRelationOptions` key (an array key), so since the initial commit every generated Create/Edit page ran `list()` for all relations on the server, threw the result away, and the client fetched everything again. Fixing the key contract in one shared helper makes the SSR prefetch real (options present on first paint, no skeleton), removes the wasted server reads structurally (the same helper decides for hook, loader and generator), and removes the service map from generated code (registry resolution).
