change: `checkScreenImports` (pnpm test:screens) no longer assumes the flat `components/<Name>` layout. New rule: a directory under `features/<d>/components/` that has `index.tsx` is a section container WITH parts; a Screen import whose path passes THROUGH such a directory (`<Name>/<Part>`, `Admin/<Name>/<Part>`) fails. Directories without `index.tsx` are namespaces and are passed through: grouping such as `components/Admin/<Name>`, `components/admin/<Name>`, `components/Mobile/<Name>`, `components/common/<Name>` is allowed, and an `index.ts`-only directory (barrel) counts as a namespace. The special "common/ is parts" error is removed (`common/` for shared parts stays as upstream's placement convention, documented, not enforced). `checks.mjs` stays pure: `checkScreenImports(source, { isContainerDir })` takes a predicate; `screens.test.mjs` exports `isContainerDir(dirSpec)` that resolves `@/features/<d>` like tsconfig paths (core domains → `src/features/core/<d>`) and checks for `index.tsx`. Without the option, every nested import fails (strict, unit-test default). No registry change.
why: The check shipped in 20261019-010000 (ui-layers-rename) failed every fork that groups containers by audience/surface (oripa-do: 54 false positives over ~45 Screens), although all of them import containers. The contract it protects — a Screen imports a container, not a part — does not depend on how many directory levels sit above the container. Upstream itself groups `user/components/admin/<Name>`. Flattening is NOT required: grouping dirs are a stated, allowed layout. For audience-split domains, put containers under any grouping dir you like (`components/Admin/<Name>`, `components/user/<Name>`); the only rule is that a container with parts has its body in `<Name>/index.tsx` and its parts beside it.
