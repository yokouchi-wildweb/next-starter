change: Coupon redemption gained an entry scope. `isUsable(code, userId?, options?)` / `redeem(code, userId?, meta?, tx?, options?)` / `redeemWithEffect(code, userId, meta?, tx?, options?)` / `validateCouponStatically(coupon, userId?, options?)` accept `options.scope = { types?: CouponType[]; categories?: string[] }`; a mismatch returns new `UsabilityReason` "type_mismatch" (or existing "category_mismatch") WITHOUT consuming the coupon. `isUsable` additionally accepts `skipRedeemerChecks: true` (pre-login preview only; `RedeemOptions` rejects it by type). Core entries are now scoped: auth `register()` accepts type=invite only (`INVITE_CODE_REDEEM_SCOPE`, referral/constants/inviteCodeScope.ts), `completePurchase` accepts category=purchase_discount only, `POST /api/coupon/redeem` accepts type=official only. New public rate-limited `POST /api/referral/validate-invite-code` → `{ valid: true } | { valid: false, message }` (no reason, no coupon info) + client `validateInviteCode` / manual-trigger hook `useValidateInviteCode` (referral, same shape as useValidateCouponForCategory) + `useInviteCodeValidation` / `InviteCodeField` (auth). Email/OAuth signup forms now have an explicit 適用 button on the invite field (same operation model as the purchase-page CouponInput: input + 適用 → green applied box with 取り消す, or red error), prefilled invite-link codes are auto-applied once, and submit is blocked while unapplied text remains in the field. No automatic per-keystroke validation. `POST /api/auth/register` response gained `inviteCode: { applied, reason? } | null`.
why: Without scope, any active coupon typed into the signup invite field was consumed: current_total_uses incremented, history written, but the referral handler never ran (category mismatch) → no referrals row, signup/purchase rewards lost for inviter and invitee, issuer quota burned by phantom uses (pandora incident 2026-09-08/13). The generic guest redeem route had the same hole. Downstream code that calls redeem/redeemWithEffect for its own entries (issuer programs, campaign forms) is still unscoped until it passes `scope`; `Record<UsabilityReason, ...>` maps now need the "type_mismatch" key.

notes: Defaults are backward compatible — omitting `options` keeps the old behavior for downstream callers, but the three core entries above changed behavior on purpose. The pre-login validation deliberately returns one message for not_found / inactive / expired / type_mismatch / max_total_reached (enumeration guard) and never returns inviter name or coupon metadata; if a downstream wants "○○さんからの招待" it must ship its own route and accept the PII exposure. Registration still does NOT fail when the invite code cannot be applied (multi-step Firebase flow cannot be rolled back) — the form-side block is the UX guard, the server scope is the accounting guard. `skipRedeemerChecks` exists only because invite codes carry max_uses_per_redeemer=1 which forces `user_id_required` when no user is known; the final redeem re-runs every check with the user. Remediation of already-consumed phantom uses is NOT automated (histories carry no entry context); registration now records `metadata.entryPoint = "registration"` so future audits can distinguish entries. Recommended but not shipped: add `rateLimit: "apiGeneral"` to `POST /api/coupon/check-usability` (it already returns coupon name/type for any code without auth).
