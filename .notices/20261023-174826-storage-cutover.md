change: N2 of the storage redesign (needs N1 storage-foundation applied first). Everything that stores, shows or deletes files now goes through the N1 base and the old path is deleted without shims. (1) Generated output: media fields get `storageMediaValueSchema` (Multi = array), drizzleBase passes `storage: storageBindingFor(...)` (no storageCleanupFields, no wrappers/duplicate), presenters resolve refs via formatMediaThumbnail(s), generated <Domain>Fields set `purpose: "<domain>.<field>"`; Firestore domains with media fields stop generation. (2) MediaUploader / MediaUploaderMulti / ControlledMediaUploader / ControlledMediaField: prop `uploadPath` removed, `purpose` required, value = storage ref, new `reencodeImage` (default on). usePendingMediaDeletion is a no-op (adopted files are detached by the business save on the server). (3) Call sites: avatar = purpose user.avatar (useAvatarUpload, AccountAvatarSection prop storagePath removed, UserUpdateByAdminSchema includes avatarUrl), chat = chatRoom.image|video|file with scopeId roomId, bank transfer proof = purchaseRequest.bankProof (ref of the requester for the same request), notification image / coupon image via binding, demo.media is admin-only, mediaProbe takes `{ ref }` and limits storagePath to the legacy bucket, dataMigration import copies old own-bucket URLs into new refs and export resolves refs with the runner's read check. (4) Save rules: a changed media value must be a managed ref; create accepts refs only; an unchanged old URL can be kept; "/"-prefixed media values fail validation on an edit save. (5) Deleted (no shims): see notes. (6) Firebase Storage: `storage.rules` (deny-all) and `firebase.json` are now tracked and shipped (removed from .gitignore). (7) docs/setup §6.1, scripts/README, .env.example (STORAGE_* lines are now real empty keys), env:init message, CLAUDE.md (STACK storage line, BACKEND_DOCTRINE, CRUD_SERVICE `media_columns` MANDATORY line; `sql_template_date` + `requestMemo_rule` merged into `raw_sql`).
why: The old path let any logged-in user overwrite or delete any object through the client SDK (rules were `auth != null`) and the server upload / delete routes had no owner checks (emergency notice 20261022-190000 restricted them to admins). After N2 the app server is the only judge, files are tracked in the storage_objects ledger and bound to business rows in the same transaction, and the client SDK path is closed by deny-all rules. Forks must move their call sites, generated files and profile / custom media code to the new base, otherwise tsc fails (removed props / exports) or saves are rejected with 400.
required_actions:
1. Before merging: if the fork has an untracked `firebase.json` or `storage.rules` (both used to be in .gitignore), move them aside (e.g. `mv firebase.json /tmp/<fork>-firebase.json.bak`, same for storage.rules), otherwise git refuses the merge ("untracked working tree files would be overwritten"). Keep `.firebaserc` / `firestore.rules` / `firestore.indexes.json` as they are (still ignored).
2. Merge upstream. Conflict policy: modify/delete on a deleted path (notes "deleted") → take the deletion and move the fork's use to the new API (do not restore the file); `storage.rules` → take upstream (deny-all, do not keep fork rules); `.gitignore` → keep the upstream removal of `firebase.json` and `storage.rules` plus the fork's own lines; `CLAUDE.md` → upstream.
3. If the fork's old firebase.json (from step 1) had other sections (firestore, hosting, emulators, ...), add them back to the tracked firebase.json next to the `"storage"` key. Never change the `"storage": { "rules": "storage.rules" }` entry.
4. `pnpm dc:generate:all --yes` (regenerates media fields, drizzleBase bindings, presenters, Fields with purpose, AUTO purposes). If it stops on a Firestore domain with media fields, the field cannot stay a media field on Firestore: move the domain to Neon or drop the media field (decide with the human). If it stops on `storage.visibility`, declare it in domain.json as in N1.
5. Every write-once `services/server/<domain>Service.ts` that still has `import { duplicate } from "./wrappers/duplicate"` and `duplicate,`: remove both and delete `wrappers/duplicate.ts` if it only did the old storage copy (keeping it makes duplicate fail with 400 because it copies to old URLs). A custom duplicate that must copy media uses `storageBinding.duplicateValues(record)` (pattern: src/features/core/coupon/services/server/wrappers/duplicate.ts).
6. Run `pnpm typecheck` and move every call site it reports: `uploadPath=` → `purpose="<registered purpose>"`; appStorageClient / useAppStorage / clientUploader / directStorageClient / useDirectStorage → `uploadToStorage` from `@/lib/storage/client` called inside a lib part (MediaUploader*) or a domain hook, never from a UI part; uploadFileServer / copyFileServer / deleteFileServer → `storageObjectService.putFromServer` / `copy` / `remove` (`@/features/core/storageObject/services/server`); getPathFromStorageUrl → `parseLegacyStorageUrl` (`@/lib/storage/server`, legacy URLs only); `storageCleanupFields` → the createCrudService `storage` option (`storageBindingFor`); `import { storage } from "@/lib/firebase/client/app"` → removed (no client SDK storage); `PENDING_IMAGE_PLACEHOLDER`, `useMockUploader`, `FieldConfig.uploadPath`, `AccountAvatarSection` `storagePath` → delete the use. Each new purpose the fork needs goes into the FORK block of src/registry/storagePurposeRegistry.ts (`pnpm test:storage-purposes`).
7. Hand-written FieldRenderer forms with media fields: pass `purpose` (e.g. via fieldPatches) for each media field; a media field without purpose renders a "purpose not set" notice instead of an uploader.
8. Server code that inserts or updates media columns outside createCrudService (raw insert, systemUpdate, copying a ref from another row or table): change it to go through the binding (service create / update) or `storageObjectService.attach` in the same TX (pattern: notification sendDirect), and use `storageObjectService.copy` when another row needs the same file. Otherwise the file stays unadopted and storage-sweep deletes it.
9. Remove `uploadPath` from domain.json media fields (now unused; dc:init no longer asks it) and from role.json profile fields.
10. `pnpm db:push:check` must report 0 statements (N2 has no DDL).
