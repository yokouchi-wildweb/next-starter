checkpoint: deprecated-aliases-removal
change: Every `@deprecated` alias / compat re-export in upstream core is deleted (no replacement behavior is removed except the legacy search-priority ordering, see 8). (1) Text tone aliases `notice` / `caution` → `warning`, `error` / `danger` → `destructive` (`textVariants.tone`, so `Para` / `SecTitle` / every TextBlocks `tone`); FieldRenderer `description.tone` union `"danger"` → `"destructive"`. (2) `SwitchInput` `activeColor` / `inactiveColor` `"error"` → `"destructive"`. (3) `DetailModalBadge.colorClass` → `variant` (`BadgeVariant`). (4) `src/utils/siteTheme.ts`: `getInitialTheme()` → `resolveCurrentSiteTheme().isDark`; `applyTheme(isDark)` → `applyThemeToDom(isDark)` + `persistThemePreference(isDark)` (persist only on a user toggle). (5) `containerClassName` prop of `DateInput` / `TimeInput` / `DatetimeInput` → `className`. (6) Type/const aliases: `ManualFieldGroupDescription` → `FieldItemDescription`; `RECAPTCHA_INTERNALS` → `RECAPTCHA_V3_INTERNALS`; `@/lib/structuredDocument` aliases `StructuredDocument` / `DocumentSection` / `SectionNumbering` / `RenderMode` / `StructuredDocumentRendererProps` / `StructuredDocumentRenderer` → `LegalDocument` / `LegalSection` / `LegalSectionNumbering` / `LegalRenderMode` / `LegalDocumentRendererProps` / `LegalDocumentRenderer`. (7) Compat re-exports removed: `@/lib/aiVision/client` (file deleted) → `@/lib/ai/client`; `AudioEngine` from `@/lib/seamlessVideo` → `@/lib/webAudio`; `MediaState` / `MediaHandleEntry` from `FieldRenderer/FieldRenderer` → `@/components/Form/FieldRenderer/types` (or the `@/components/Form` barrel); `CellAction` from `@/lib/tableSuite/DataTable` → `@/lib/tableSuite/types` (or the `@/lib/tableSuite` barrel); `getRelations` / `getHasManyRelations` / `resolveJunction*` / relation types from `@/lib/dataMigration/relations` → `@/lib/domain`. (8) crud legacy search priority: `SearchParams.searchPriorityFields` / `prioritizeSearchHits`, service options `defaultSearchPriorityFields` / `prioritizeSearchHitsByDefault`, `buildSearchPriorityOrderBy` (`@/lib/crud/drizzle`), `parseSearchPriorityFields` (`src/app/api/[domain]/search/utils.ts`) and the matching query params of `GET /api/[domain]/search` / `/api/profile/[role]/search` are deleted. Ordering without `searchRank` is now plain `orderBy` (+ id). In base `search()` the old default (`prioritizeSearchHits` false) put the CASE clauses after the unique id tiebreak, so it had no effect there; only explicit `prioritizeSearchHits: true` changes. CORRECTION (see 20261019-141500-search-wrapper-id-tiebreak): fork wrappers that copied the ordering but built it from `buildOrderBy` alone (no id tiebreak) DID use the CASE clauses to order rows tied on `orderBy` when a keyword was given — removing the branch leaves those ties unordered, so close the ordering with `withIdTiebreak` as in step 3b. Unknown query params are ignored, so old clients sending them do not error.
why: These aliases were kept "for compatibility" with no removal date; the new names have existed for several checkpoints (tone/variant/siteTheme since the style-ownership work, searchRank since 20261011). Deprecated paths that never go away keep being copied into new code.
required_actions:
1. Merge upstream. Conflicts only if your fork edited the files that held the aliases (textVariants, SwitchInput, DetailModal/types, utils/siteTheme, Date/Time/DatetimeInput, crud types/service/buildSearchRank, the two search routes + utils): take upstream and re-apply your own non-alias edits.
2. Run `pnpm tsc --noEmit`. Every leftover is a type error; fix each with the mapping in change (1)–(7). Typical: `tone="error"` / `"danger"` → `"destructive"`, `tone="notice"` / `"caution"` → `"warning"`, `activeColor="error"` → `"destructive"`, view-modal hooks returning `badge: { text, colorClass: "bg-..." }` → `badge: { text, variant: "<BadgeVariant>" }` (pick the semantic variant the raw color meant; raw palette classes no longer reach the badge).
3. Search priority (change 8). (a) Your own search routes that copied the generic one (`parseSearchPriorityFields` import, `searchPriorityFields` / `prioritizeSearchHits` locals): delete those lines; keep `parseSearchRank`. (b) Your search wrappers that copied the base `search()` ordering (`buildSearchPriorityOrderBy`, `priorityOrderClauses`, `prioritizeSearchHits`): delete the priority branch and close the ordering with the id tiebreak like base `search()` does: `const orderClauses = [...(rankOrderClause ? [rankOrderClause] : []), ...orderByClauses, ...(orderBy?.some(([f]) => f === "id") ? [] : [asc(<Table>.id)])];` — without it, rows tied on `orderBy` have no defined order (they used to be ordered by the hit CASE when a keyword was given). The later notice 20261019-141500-search-wrapper-id-tiebreak replaces this inline form with the helper `withIdTiebreak`. If hit-first ordering is wanted, pass `searchRank: true` (see 3c). (c) Callers passing `searchPriorityFields` / `prioritizeSearchHits: true` that relied on hit-first ordering: pass `searchRank: true` (or `{ fields: [{ field, weight }] }`), and for a service default set `defaultSearchRank` (domain.json `searchRank` key for business domains, then `pnpm dc:generate -- <Domain>`).
