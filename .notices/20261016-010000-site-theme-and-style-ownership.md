change: (1) Style ownership split: color VALUES moved out of `src/styles/theme.css` (`:root` / `.dark` blocks) into upstream-owned `src/styles/palette.defaults.css`; new downstream-owned `src/styles/custom/{index,palette,typography,overrides}.css` imported LAST in `global.css` (write only the values you change; upstream never edits `custom/`). (2) Site theme config: new `src/config/ui/site-theme.config.ts` = `defineSiteThemeConfig({...partial})` over lib defaults (`@/lib/siteTheme`): per-area `mode: light|dark|system` + `switchable`, path-prefix areas (default `admin` = /admin,/debug switchable; fallback `user` locked light). Root layout now SSR-renders `<html class="dark" data-area="...">` from `x-pathname`, injects a head bootstrap script (stored preference + prefers-color-scheme, no first-paint flash), and mounts `SiteThemeSync` (sole DOM writer on client navigation / toggle / OS change). `theme.css` gains `color-scheme`. (3) `APP_FEATURES.adminConsole.enableDarkModeSwitch` REMOVED — `DarkModeSwitch` self-hides when the current area is not switchable. (4) `scripts/mail/generate-colors.ts` now reads `palette.defaults.css` + `custom/palette.css` (merged `:root`) and fails before writing if a target var is missing. (5) `src/utils/siteTheme.ts` rewritten: `applyThemeToDom` (DOM only) / `persistThemePreference` (storage only, called on user toggle only); old `getInitialTheme` / `applyTheme` kept as @deprecated aliases. (6) Light-only colors tokenized: Dialog close button (`bg-black text-white` → `bg-foreground text-background`), StepperInput unit label (`bg-gray-700 text-white` → `bg-foreground text-background`; in light mode the label is now near-black instead of dark gray, in dark mode it inverts to near-white with dark text). (7) `color-scheme: light|dark` added on `:root` / `.dark` in theme.css — native controls (scrollbars, select popups, date pickers) now render dark inside dark areas; a fork that already sets `<meta name="color-scheme">` or its own `color-scheme` CSS should drop the duplicate.
why: Downstreams could not set a dark-first user side without editing core (light default hardcoded in theme.css / getInitialTheme / DarkModeSwitch bootstrap), and the admin DarkModeSwitch writing "light"/"dark" to localStorage leaked into the user side on client navigation (single `<html>` root). More generally, every design change required editing upstream-owned files → merge conflicts on every upstream token change. This is step 1 of the design-freedom roadmap (ownership split + defaults/override model); later steps (fonts config, semantic text tokens, variant override map, raw-palette lint, core UI sweep) build on it.
