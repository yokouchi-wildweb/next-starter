change: (1) New build-time guard `pnpm styles:check-build` (scripts/styles/check-built-css.ts + builtCss.ts): walks every relative `@import` reachable from `src/styles/global.css` (including `custom/`), collects the CSS custom properties each file declares outside `@theme` / `@utility`, and fails if any name is absent from `.next/static/**/*.css`. `pnpm build` now ends with it (`... && next build && pnpm styles:check-build`), so a Vercel build whose CSS lost an @import target fails instead of going live broken. Files that only override names declared elsewhere (e.g. `custom/palette.css` setting just `--primary`) cannot be verified and get a warning. (2) Test `pnpm test:built-css`. (3) Durable rule in `src/styles/README.md`「デプロイ後の確認(Vercel ビルドキャッシュ)」and setup doc §6: the first prod deploy after merging CSS-adding notices is done without build cache.
why: Incident in a fork (2026-10-27): prod had stayed on a 10/10 build, then 17 days of upstream merges were deployed at once. The Vercel build restored the stale build cache and the output CSS silently lacked exactly the 3 @import targets added since (palette.defaults.css, typography.defaults.css, custom/index.css) — `--primary`, `--radius`, `--font-geist-sans` undefined, whole palette / radius / fonts lost. Local dev and a local `next build` of the same commit were fine. A redeploy with build cache skipped fixed it. Every fork inherits global.css + custom/ and the CSS-adding notices (20261016-010000, 20261016-020000, 20261017-010000), so any fork that deploys rarely or merges many notices at once is exposed. Editing those past notices does not reach forks that already applied them (applied ids never resurface), hence this notice.
required_actions:
1. Merge upstream. Possible one-time conflict only if your fork edited the `build` script in `package.json`: keep your changes and make sure the line still ends with `&& pnpm styles:check-build`.
2. Check whether your current prod is affected: open the prod site, take the stylesheet URLs from `<link rel="stylesheet" href="/_next/static/...css">` in view-source, fetch each (`curl -s <url>`) and grep for `--primary:` and `--font-geist-sans:`. Both present = fine. Either absent = your prod CSS is missing @import targets → do manual_steps now.
3. If your Vercel project's Build Command is not `pnpm build` (Settings → Build and Deployment → Build Command; default = framework preset `next build`), the guard does not run on Vercel: set the Build Command to `pnpm build` (same requirement already applies to `cron:check --vercel-build`), or run `pnpm styles:check-build` after your own build step.
4. From now on: after merging any upstream notice that adds or restructures CSS files (notes of such notices point here), make the first prod deploy without build cache (see manual_steps). Do NOT disable the build cache permanently (Hobby-plan build CPU); `VERCEL_FORCE_NO_BUILD_CACHE` is a temporary toggle only.
verify: `pnpm test:built-css` passes; `pnpm typecheck` passes; `pnpm build` locally ends with `✓ styles:check-build: <n> ファイル / <m> 変数が ... 揃っています`; the prod CSS fetched in step 2 contains `--primary:` and `--font-geist-sans:`; the next Vercel build log shows the same `✓ styles:check-build` line.
manual_steps: Redeploy without build cache when step 2 found missing tokens, or for the first prod deploy after this merge if your prod has not been deployed since 2026-10-16: `pnpm deploy:all -- --prod --force` (vercel CLI; `--force` skips the build cache), or Vercel dashboard → Deployments → Redeploy with "Use existing Build Cache" unchecked, or set env `VERCEL_FORCE_NO_BUILD_CACHE=1`, redeploy, then remove the env var.

notes: Cause attribution (stale Turbopack cache not reconciling new @import targets) comes from comparing Vercel build logs of the same commit — "Restored build cache from previous deployment" (broken) vs "Skipping build cache" (good); the bundler internals were not reproduced locally, so the guard checks the output, not the cause. The guard matches names only (`--name:`), because the minifier rewrites values (oklch → hex + lab fallback). Upstream files each declare unique names, so their loss is always caught; a fork's `custom/*.css` is only verifiable once it declares at least one fork-specific variable (the guard prints a warning otherwise, no failure). Local false positive = stale `.next` from an older source: delete `.next` and rebuild.
