# 新規プロジェクトの立ち上げ: フォークからデプロイまで

このリポジトリ(next-starter = Tier1)をフォークして新しいプロジェクトを立ち上げる手順です。
clone から、フォーク固有ファイルの書き換え、最小構成での起動確認、バックエンド接続、Vercel へのデプロイ、上流追随の準備までを一本の流れで扱います。

**この文書はリポジトリの外の手順(GitHub・Vercel・外部サービス)の正です。** リポジトリの中の段取り(リモートの組み替え・fork の名前・追随台帳・package 名・事業の素性・機能の入切・`.env.development`・`vercel.json`・`project.md`・初期コミットと push)は `/fork-init` が持ちます。本体は命令 `pnpm workflow fork-init` で、書く物の表は `scripts/workflow/fork-init/README.md` にあります。

---

## 1. 前提

### 用語

| 用語 | 意味 |
|---|---|
| upstream | フォーク元。通常は next-starter(Tier1) |
| origin | 新しく作るプロジェクトのリポジトリ |
| fork の名前 | 各リポがリポ直下の `repo.json` の `repo_id` に書く短い名前(小文字・数字・ハイフン。Tier1 = `next-starter`)。追随台帳 `.notices/applied/<名前>.md`・一時許可・`src/lib/CATALOG.md` の自分の節の見出し・注文の受信箱に同じ値を使う。origin の URL からは導かない。祖先や既存のプロジェクト(リポの一覧・受信箱)と同じ名前は使えない(`/fork-init` が確かめる) |

Tier の考え方(Tier1 → Tier2 → Tier3)は `.claude/rules/project.md` の TIER 節を参照してください。本手順は T1→T2 だけでなく T2→T3 のフォークでもそのまま使えます。

### 必要なツール

| ツール | 用途 | 確認コマンド |
|---|---|---|
| Node.js 20.9 以上 | Next.js 16 の要件 | `node -v` |
| pnpm | パッケージマネージャ(npm は使わない) | `pnpm -v` |
| git + SSH 鍵 | clone / push | `ssh -T git@github.com` |
| gh CLI(ログイン済み) | GitHub リポジトリ作成 | `gh auth status` |
| vercel CLI | デプロイ時のみ | `vercel --version` |
| tmux | ターミナルの claude を tmux で開き、エージェントが開発サーバーのタブを自分で立てる(手順 4「tmux で開く設定」) | `tmux -V` |

`gh` が未インストールなら `sudo apt install gh` のあと `gh auth login`(GitHub.com / SSH / ブラウザ認証)。ブラウザに表示される「Enter the code」はターミナルに出た `XXXX-XXXX` のワンタイムコードのことで、二段階認証とは別物です。

## 2. リポジトリの作成と clone

upstream の全履歴を保持したまま clone します。履歴を捨てると `/flux` による上流追随ができなくなるため、shallow clone や「ファイルコピーして git init」は使いません。

```bash
# upstream を全履歴ごと clone
git clone git@github.com:yokouchi-wildweb/next-starter.git ~/projects/<name>
cd ~/projects/<name>
```

ここまで済んだら `claude` を起動して `/fork-init <name> [github-owner]` を実行します。聞かれたことに 1 回で答え、計画を 1 回承認すると、GitHub の private リポジトリの作成(説明欄 = プロジェクト名の置き場)・依存のインストール・リポジトリの中の書き換え・初期コミットと push・手元の許可の設定(`/local-settings`)・tmux で開く設定まで進みます。走らせ直しても済んだ手順は飛ばします。

## 3. 最小構成で起動する(バックエンド未接続)

Firebase と DB が未設定でも、次の 3 つがあれば開発サーバーは起動します。試験的なプロジェクトはまずここまでで動かし、バックエンドは必要になった時点で接続します。

```bash
pnpm ops setup env
```

`.env.example` を `.env.development` にコピーし、次の値を自動で埋めます(既存ファイルがあれば何もしません)。

| 変数 | 値 | 備考 |
|---|---|---|
| `APP_BASE_URL` | `http://localhost:3000` | ローカル用 |
| `AUTH_JWT_SECRET` | ランダム 32 バイト(base64) | 未設定だとセッション処理で例外 |
| `ENCRYPTION_KEY` | ランダム 32 バイト(hex 64 文字) | トークン暗号化用 |

`.env*` は gitignore 対象です。コミットされないことを `git status` で確認してください。

```bash
pnpm dev
# http://localhost:3000 が開けば OK
```

エージェントが確かめるときは `pnpm workflow dev-tab run` で tmux のタブ(tmux を使わない設定・tmux が無ければ裏のプロセス)に立てる(空きポートを選ぶ。止めるのは `pnpm workflow dev-tab run stop`。`scripts/workflow/dev-tab/README.md`)。ログインが要る確認は `pnpm workflow dev-admin run` のテスト用の管理者で入る(`scripts/workflow/dev-admin/README.md`)。

### 機能別に必要なバックエンド(目安)

| 使いたい機能 | 必要な設定 |
|---|---|
| ログイン / ユーザー / 管理画面 | Firebase Auth + `DATABASE_URL`(Neon) |
| 業務ドメイン(pnpm generate domain で作る CRUD) | `DATABASE_URL` |
| 画像・動画アップロード | 新しい公開 / 非公開バケット(`pnpm ops storage setup`)+ `STORAGE_PUBLIC_BUCKET` / `STORAGE_PRIVATE_BUCKET` 等。Firebase Storage には全拒否の `storage.rules` を配備 |
| リアルタイム配信 | Firestore、または servers/room |
| メール送信 | `RESEND_API_KEY` 等(`MAIL_PROVIDER` 参照) |
| 定期タスク(本番) | `CRON_SECRET` + `vercel.json`(`/fork-init` が生成済み) |

### 両方未設定の状態で動く範囲

DB も Firebase も未設定のままで動くのは、トップページ、`/demo` 配下のコンポーネントデモ、利用規約などの静的ページ、`GET /api/health` です。管理画面のシステム設定（メンテナンスモード等）は「未保存」と同じ既定値で扱われます。ログイン・管理画面・業務ドメインの API は、未設定のまま叩くと接続待ちをせず即座にエラー（`DatabaseNotConfiguredError` / `FirebaseNotConfiguredError`）になります。判定は「環境変数が空」のときだけで、設定済みで接続できない場合は通常のエラーとして表面化します。

設定手順は [Neon Firebase など各種バックエンドサービスの設定方法](Neon_Firebaseなど各種バックエンドサービスの設定方法.md) を参照してください。
`DATABASE_URL` を設定したら `pnpm db:push` でスキーマを適用します(対話プロンプトが出るため人間が実行する)。

## 4. /fork-init が書く物

リポジトリの中の書き換えは `/fork-init`(本体 `pnpm workflow fork-init plan|apply`)が答えのファイル 1 つから行います。何を書くか・どう済みを判定するかの表は `scripts/workflow/fork-init/README.md` が正です。

- `project.md` は雛形(`scripts/workflow/fork-init/project.template.md`、見出し overview / tier_only / maker)から書き、決まっていない行は `TBD` のまま残ります。決まったら埋めてください
- `behavior.md` は fork 元の版のままで始めてよい(各リポが自分の版を持つ)
- `README.md` は書き換えません(全リポジトリ共通。固有の情報は `project.md` と GitHub の説明欄)
- `.env.development` はコミットしません

### tmux で開く設定(マシンごとに 1 回)

ターミナルで打った `claude` が tmux の中で開くようにする。エージェントが開発サーバーを同じ tmux のタブで自分で立てて確かめるための前提。同じマシンで 2 つ目以降のフォークには要らない(`/fork-init` も済んでいれば飛ばす)。

```bash
pnpm workflow tmux-launch setup --check   # 入っているか
pnpm workflow tmux-launch setup           # 入れる(~/.bashrc か ~/.zshrc に 1 行、~/.tmux.conf に設定の塊)
```

- tmux が無ければ先に入れる(`sudo apt install tmux` / `brew install tmux`。sudo のパスワードが要るので人が打つ)
- 入れたら新しいターミナルで `claude` を打ち直す(会話の続きは `claude --continue`)
- 未設定のマシンで claude を起動すると、SessionStart hook がエージェントに知らせる。詳細: `scripts/workflow/tmux-launch/README.md`

`.env.production` を使う場合は `.env.development` と同じキーを本番の値で用意します。Vercel にデプロイする場合、環境変数は Vercel 側に登録するため `.env.production` は不要です(ローカル本番ビルドの確認用)。

## 6. Vercel へのデプロイ

デプロイ先は Vercel です。Firebase Hosting / App Hosting は使いません。

```bash
npm i -g vercel        # 未インストールの場合
vercel link            # 初回のみ。Vercel プロジェクトと紐付け
```

1. **環境変数**: Vercel ダッシュボードの Settings > Environment Variables に `.env.development` と同じキーを本番の値で登録します(Production / Preview を分ける)。`APP_BASE_URL` は Preview では未設定でよく(`VERCEL_URL` を自動検出)、Production には正式 URL を入れます
2. **定期タスク**: `vercel.json` の crons は `/fork-init` が `pnpm generate cron -- --plan hobby|pro` で生成済みです。Vercel の環境変数に `CRON_SECRET` を登録してください(未登録だと全 cron が 401 で止まります)。タスクの増減やプラン変更のたびに同じコマンドで再生成します。`vercel.json` が `src/app/api/cron/*/task.ts` と食い違うと、Vercel 上のビルド(`pnpm build` 冒頭の `pnpm check cron -- --vercel-build`)と `pnpm live` 系(`pnpm live`・`pnpm live:room`・`pnpm live:all`)が止まります。詳細は [src/lib/cron/README.md](../../src/lib/cron/README.md#スケジュールのセットアップ)
3. **デプロイ**:
   ```bash
   pnpm live:all                       # 本番(vercel --prod)
   pnpm live:all -- --target=preview   # プレビュー
   ```
   `pnpm live:all` はリアルタイムルーム基盤(servers/room)が有効ならそちらを先にデプロイし、無効ならアプリだけをデプロイします。アプリだけは `pnpm live`(= `pnpm live:app`)、ルームサーバーだけは `pnpm live:room`。詳細は `scripts/operations/deploy/` の各ファイル冒頭のコメント
   CSS ファイルを足す上流 notice をまとめて取り込んだ直後の初回本番デプロイは、ビルドキャッシュを使わず `pnpm live -- --prod --force` で行います(古いキャッシュが新しい `@import` 先を落とし、本番だけ見た目が崩れることがある。`pnpm build` 末尾の段階 `pnpm check --phase=build:post` の `pnpm check styles` が検出してビルドを止めます)。詳細は [src/styles/README.md](../../src/styles/README.md#デプロイ後の確認vercel-ビルドキャッシュ)
4. **独自ドメイン**: Vercel ダッシュボードの Settings > Domains で追加し、指示された DNS レコードを登録します。証明書は自動発行です。Firebase Auth の承認済みドメインと OAuth のリダイレクト URI も独自ドメインに更新してください

## 7. 上流追随の準備

フォーク後も upstream の改善を取り込み続けます。

- 取り込み: `/flux`(fetch → 未適用 notice の検出と区間分け → 全区間の概観と次の区間の計画 → 承認 → その区間の merge・適用・上流の変更への追従・検査・台帳記録・コミット → 次の区間の計画を出して止まる。承認は区間ごと、`/flux all` で最後まで)
- 状態確認のみ: `/flux status`
- 汎用機能が必要になったとき: 自前実装せず `/order <上流リポ>` で upstream に依頼し、`/wen` で状況を追う

仕組みの詳細は `.notices/README.md` を参照してください。

## 8. トラブルシューティング

- **`AUTH_JWT_SECRET が設定されていません`**: `.env.development` に値を入れ、dev サーバーを再起動する
- **meta description やメール送信者名に `next-starter` が出る**: `src/business/business.ts` が例の値のまま(`/fork-init` の答えで書くか、後で直す)
- **Claude が「このリポジトリは Tier1」として振る舞う**: `.claude/rules/project.md` が fork 元の版のまま(`/fork-init` を走らせ直すと雛形から書く)
- **`/flux` が shallow clone と報告する**: `git fetch --unshallow upstream` で履歴を補完する
- **Drizzle の接続エラー**: `DATABASE_URL` の権限と IP 許可リストを確認する
