# 新規プロジェクトの立ち上げ: フォークからデプロイまで

このリポジトリ(next-starter = Tier1)をフォークして新しいプロジェクトを立ち上げる手順です。
clone から、フォーク固有ファイルの書き換え、最小構成での起動確認、バックエンド接続、Vercel へのデプロイ、上流追随の準備までを一本の流れで扱います。

**この文書が手順の正です。** `/fork-init` スキルは本文書の「4. フォーク固有ファイルのチェックリスト」までを承認1回で実行する実行役であり、独自の手順を持ちません。手順を変えるときは本文書を直し、スキルはそれに従わせます。

---

## 1. 前提

### 用語

| 用語 | 意味 |
|---|---|
| upstream | フォーク元。通常は next-starter(Tier1) |
| origin | 新しく作るプロジェクトのリポジトリ |
| fork-id | origin URL のパス部分を `--` 連結・小文字化したもの。例: `git@github.com:acme/shop.git` → `acme--shop`。追随台帳のファイル名に使う |

Tier の考え方(Tier1 → Tier2 → Tier3)は `.claude/rules/project.md` の TIER 節を参照してください。本手順は T1→T2 だけでなく T2→T3 のフォークでもそのまま使えます。

### 必要なツール

| ツール | 用途 | 確認コマンド |
|---|---|---|
| Node.js 20.9 以上 | Next.js 16 の要件 | `node -v` |
| pnpm | パッケージマネージャ(npm は使わない) | `pnpm -v` |
| git + SSH 鍵 | clone / push | `ssh -T git@github.com` |
| gh CLI(ログイン済み) | GitHub リポジトリ作成 | `gh auth status` |
| vercel CLI | デプロイ時のみ | `vercel --version` |

`gh` が未インストールなら `sudo apt install gh` のあと `gh auth login`(GitHub.com / SSH / ブラウザ認証)。ブラウザに表示される「Enter the code」はターミナルに出た `XXXX-XXXX` のワンタイムコードのことで、二段階認証とは別物です。

## 2. リポジトリの作成と clone

upstream の全履歴を保持したまま clone します。履歴を捨てると `/flux` による上流追随ができなくなるため、shallow clone や「ファイルコピーして git init」は使いません。

```bash
# 1. GitHub に空の private リポジトリを作る(README なし)
gh repo create <owner>/<name> --private

# 2. upstream を全履歴ごと clone
git clone git@github.com:yokouchi-wildweb/next-starter.git ~/projects/<name>
cd ~/projects/<name>

# 3. リモートを整理: origin = 新リポ、upstream = フォーク元
git remote rename origin upstream
git remote add origin git@github.com:<owner>/<name>.git

# 4. 依存インストール
pnpm install
```

ここまで済んだら、以降の手順 3〜4 は `claude` を起動して `/fork-init` に任せられます。手動で進める場合はそのまま読み進めてください。

## 3. 最小構成で起動する(バックエンド未接続)

Firebase と DB が未設定でも、次の 3 つがあれば開発サーバーは起動します。試験的なプロジェクトはまずここまでで動かし、バックエンドは必要になった時点で接続します。

```bash
cp .env.example .env.development
```

`.env.development` で最低限埋める値:

| 変数 | 値 | 備考 |
|---|---|---|
| `APP_BASE_URL` | `http://localhost:3000` | 既定値は upstream の URL なので必ず書き換える |
| `AUTH_JWT_SECRET` | `openssl rand -base64 32` の出力 | 未設定だとセッション処理で例外 |
| `ENCRYPTION_KEY` | `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"` の出力 | 64 文字 hex |

`.env*` は gitignore 対象です。コミットされないことを `git status` で確認してください。

```bash
pnpm dev
# http://localhost:3000 が開けば OK
```

### 機能別に必要なバックエンド(目安)

| 使いたい機能 | 必要な設定 |
|---|---|
| ログイン / ユーザー / 管理画面 | Firebase Auth + `DATABASE_URL`(Neon) |
| 業務ドメイン(dc:generate で作る CRUD) | `DATABASE_URL` |
| 画像・動画アップロード | Firebase Storage(+ 必要なら CORS 設定) |
| リアルタイム配信 | Firestore、または servers/room |
| メール送信 | `RESEND_API_KEY` 等(`MAIL_PROVIDER` 参照) |
| 定期タスク(本番) | `CRON_SECRET` + `vercel.json` |

設定手順は [Neon Firebase など各種バックエンドサービスの設定方法](Neon_Firebaseなど各種バックエンドサービスの設定方法.md) を参照してください。
`DATABASE_URL` を設定したら `pnpm db:push` でスキーマを適用します(対話プロンプトが出るため人間が実行する)。

## 4. フォーク固有ファイルのチェックリスト

upstream の名前や Tier 宣言が残っていると、メール送信者名や meta description に `next-starter` が出たり、Claude が「このリポジトリは Tier1」と誤認したりします。以下を**初期コミットで必ず**書き換えます。

| # | ファイル | やること |
|---|---|---|
| 1 | `.claude/rules/project.md` | 全面書き換え。下記「project.md の構成」参照 |
| 2 | `.notices/applied/<fork-id>.md` | 新規作成。中身は 1 行 `# APPLIED LEDGER fork:<origin url>` のみ。フォーク成立点より前の notice は `/flux` が自動で継承済み扱いにするので記録不要 |
| 3 | `package.json` | `name` をプロジェクト名に |
| 4 | `src/config/business.config.ts` | `serviceName` / `serviceNameShort` / `description` / `descriptionShort` / `domain` / `url` / `mail.defaultFrom` / `mail.defaultFromName`。未定なら仮名でよいが upstream の名前は残さない |
| 5 | `README.md` | 「プロジェクト概要」節をプロジェクトの説明に置き換える(upstream 宣言の引用ブロックを削除) |
| 6 | `.env.development` | 手順 3 のとおり。コミットしない |

### project.md の構成

upstream の `project.md` は Tier1 の宣言そのものなので、フォークでは丸ごと置き換えます。節の構成:

| 節 | 内容 |
|---|---|
| `overview` | name / type(一言) / repo(origin と upstream の URL)/ phase |
| `TIER` | `this_repo: Tier2 (direct fork of next-starter = Tier1)` のように宣言。下流を持つ予定があれば書く。汎用機能は Tier1 に `/upreq` で依頼し自前実装しない旨、`/wen` と `/flux` の案内、台帳パス |
| `backend_status` | Firebase / Neon の設定有無と、未設定なら「サーバー永続化を入れない」等の含意 |
| `direction` | プロダクトの育て方の方針(1〜3 行) |
| `domains` または `planned_tools` | 予定ドメイン。優先順があれば番号付き |
| `dev_rules` | プロジェクト固有の約束(表示コンポーネント、内部表現の正規形など)。最初は空でよい |

記述は `.claude/rules/README.md` の方針どおり英語・箇条書きです。既存フォークの例: oripa-do の `.claude/rules/project.md`。

### 初期コミット

```bash
git add .claude/rules/project.md .notices/applied/<fork-id>.md package.json src/config/business.config.ts README.md
git commit -m "chore: <name> フォーク初期設定"
git push -u origin main
```

## 5. 本番ビルドの確認

```bash
pnpm build
pnpm start   # 任意。ローカルで本番ビルドを確認
```

`.env.production` を使う場合は `.env.development` と同じキーを本番の値で用意します。Vercel にデプロイする場合、環境変数は Vercel 側に登録するため `.env.production` は不要です(ローカル本番ビルドの確認用)。

## 6. Vercel へのデプロイ

デプロイ先は Vercel です。Firebase Hosting / App Hosting は使いません。

```bash
npm i -g vercel        # 未インストールの場合
vercel link            # 初回のみ。Vercel プロジェクトと紐付け
```

1. **環境変数**: Vercel ダッシュボードの Settings > Environment Variables に `.env.development` と同じキーを本番の値で登録します(Production / Preview を分ける)。`APP_BASE_URL` は Preview では未設定でよく(`VERCEL_URL` を自動検出)、Production には正式 URL を入れます
2. **定期タスク**: 使う場合は `cp vercel.json.example vercel.json` して `CRON_SECRET` を環境変数に登録します。タスク一覧は [docs/reference/cron-tasks.md](../../reference/cron-tasks.md)
3. **デプロイ**:
   ```bash
   pnpm deploy:all                       # 本番(vercel --prod)
   pnpm deploy:all -- --target=preview   # プレビュー
   ```
   `deploy:all` はリアルタイムルーム基盤(servers/room)が有効ならそちらを先にデプロイし、無効ならアプリだけをデプロイします。詳細は `scripts/deploy.ts` 冒頭のコメント
4. **独自ドメイン**: Vercel ダッシュボードの Settings > Domains で追加し、指示された DNS レコードを登録します。証明書は自動発行です。Firebase Auth の承認済みドメインと OAuth のリダイレクト URI も独自ドメインに更新してください

## 7. 上流追随の準備

フォーク後も upstream の改善を取り込み続けます。

- 取り込み: `/flux`(fetch → merge → 未適用 notice の検出と適用 → 台帳記録 → コミットまで承認1回)
- 状態確認のみ: `/flux status`
- 汎用機能が必要になったとき: 自前実装せず `/upreq` で upstream に依頼し、`/wen` で状況を追う

仕組みの詳細は `.notices/README.md` を参照してください。

---

## 8. トラブルシューティング

- **`AUTH_JWT_SECRET が設定されていません`**: `.env.development` に値を入れ、dev サーバーを再起動する
- **meta description やメール送信者名に `next-starter` が出る**: 手順 4 の `business.config.ts` が未対応
- **Claude が「このリポジトリは Tier1」として振る舞う**: 手順 4 の `project.md` が未対応
- **`/flux` が shallow clone と報告する**: `git fetch --unshallow upstream` で履歴を補完する
- **Drizzle の接続エラー**: `DATABASE_URL` の権限と IP 許可リストを確認する
