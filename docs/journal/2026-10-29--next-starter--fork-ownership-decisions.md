# fork の所有の定義を決めた経緯

> owner: next-starter

fork が upstream のファイルをどこまで書き換えてよいか(所有の定義)を、評議会 20261022-165923-src-nondomain-followups(2026-10-23〜28、4 ラウンド)で決めた。その要点と、検討して見送った案を残す。仕様は [src/lib/forkOwnership/README.md](../../src/lib/forkOwnership/README.md)。決定番号(D<n>)は評議会の決定の番号。

## 背景

- 親の評議会(20261019-213253、共有フォルダの置き場と所有)が、所有の定義(判定の元・受け口・違反の検査・多段 Tier・導入)を残していた
- 下流の要望(20261020-160811)の所有の項目が、この決定待ちで止まっていた
- 調べた材料
  - fork 7 つすべてで、直接の親との merge-base が一意に決まり、notice の台帳とも一致した
  - 受け口の外の書き換えは 287 件。全件を分類し、103 項目について回避できるかを見ると、大半は既存の受け口か upstream の修正で避けられ、残るのは依頼から反映までの時間差だった
  - boardgame-site は既に「core を直したら上流へ依頼する」を実践していた(110 件中 80 件が依頼済み)
  - src/registry の 24 本のうち、中に区画の印を持つのは 16 本で、印の書き方は 7 通り(生成器用 2・下流用 3・upstream の手書き用 2)。fork の registry の書き換え 111 か所のうち、下流用の区画に収まっていたのは 7 か所だけだった
  - fork 7 つのうち CI があるのは 1 つだけで、取り込みごとの関門は `/flux`

## 決めたこと

- 全ファイルの持ち主は書き出さない。必要な場面ごとに必要な範囲だけ決める(D3)
- 判定 = 直接の親から最後に取り込んだ版との git の比較。所有台帳は作らない(D7)
- fork が足した物は fork の物、基準にある物は提供者の物。受け口の一覧は upstream が持ち、取り込み済みの upstream 側の版から読む(D8)
- 受け口の外の書き換えは原則失敗。まず直接の親へ依頼する。既存の受け口で済む物は受け口へ移す(D4・D11・D13)
- 受け口の無い固有機能と upstream の不具合の修正だけ、依頼の番号と blob に結び付けた一時許可で通す(D14)
- upstream が core の中の編集を案内している箇所は Tier1 の負債。負債の行として載せ、core の外に受け口を作って外す(D5・D29)
- fork は提供者のファイル・ルートを削除・移動・rename しない。止めるのは feature-gate か 1 行スイッチで、そのための feature-gate は Tier1 が用意する(D18・D19・D21)
- 祖先 Tier の lib の中への追加は失敗(D31)
- registry の所有の印は下流の印 1 種類(開始と終了の対)。生成器の区画は所有の検査の対象外(D22)
- config は再設計まで暫定で全体を受け口にする。削除は違反(D10・D35)
- 鮮度は検査のたびに親を取得して確かめ、取得できなければ「未検証」(D20)。CI は任意(D23)
- 導入時点の既存の書き換え・削除・rename は縮む区画で受け、段階的に解消させる(D17・D32)
- 段階: ① registry の印の統一 → ② 受け口の一覧と検査(報告のみ)・feature-gate の棚卸し → ③ 縮む区画の固定(D33)。fork 側の追随が大きい変更は段階的に出す(D9)

## 見送った案と理由

- 所有定義ファイル(glob でリポジトリ全体の持ち主を宣言する): git の履歴と並んで元データが 2 つになり、ずれる(D3)
- 目録(CATALOG.md)を全フォルダに広げる: 目録の整合と違反の検出は別の物で、フォルダの単位の定義にも依存する
- 基準を upstream の先端・最上位の Tier・notice 台帳の境界にする: 直接の親との merge-base が一意に決まるので足りる。台帳は照合に使う(D7・D20)
- 受け口の外の書き換えを一覧に出すだけで通す: 書き換えが溜まり、upstream が改良される流れが生まれない(D4)
- 「修正だけ先に取り込む」手段: 区間ごとの merge が崩れる(D16)
- page.tsx の削除を例外にする / 同じ URL のまま移動を許す: 消すと upstream の更新のたびに衝突する。置いておく実害は設定ミス時の公開だけで、ルート地図の差分で抑えられる(D18)
- registry の印を 2〜3 種類の対にする / 1 種類で終わりの印なし: 所有(人間・AI が書いてよいか)と生成器の区画(機械の情報)は使う相手が違う別の情報。所有は下流の印 1 種類の対で足りる(D22)
- CI を必須にする: エージェントが規則に従い `/flux` が取り込みごとの関門になる運用では追加の価値が小さい(D23)
- 中間 Tier の一覧に「下流が消してよい」行を作る: 要らない物は持ち主が自分で消して merge で流せばよい(D24)
- config の値とキーを今分ける: config 全般の再設計で決め直す(持ち越し、D10・D12)

## 異論

- CI を必須にする(席 B): 人間の判断で任意にした(D23)
- page.tsx の削除を例外にする(席 A): 人間の判断で採らなかった(D18)
