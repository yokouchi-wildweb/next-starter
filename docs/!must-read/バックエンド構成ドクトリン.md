## 決定

現行のバックエンド構成 **Firebase（Auth / Storage）+ Firestore（リアルタイム配信）+ Neon PostgreSQL（主データ、Drizzle）** を維持する。

ただし無方針の現状追認ではなく、後述の「封じ込め規律」を伴う積極的な選択として維持する。

---

## 背景

### 現構成の役割分担

| サービス | 役割 |
|---------|------|
| Firebase Auth | 認証（ソーシャルログイン、メールリンク、JWT） |
| Firebase Storage | メディアストレージ |
| Firestore | リアルタイム配信（chatRoom 等）。過去に一部ドメインの CRUD にも使われたが、新規は禁止（下記「規律 1・2」で凍結） |
| Neon PostgreSQL + Drizzle | 主データ層。audit / analytics / wallet / counting 等の横断基盤はすべてここ |

### 認識している慢性コスト

この構成には、テンプレートとして支払い続けている構造コストが 3 つある。

1. **ユーザーの二重管理** — 真実の源が Firebase Auth（認証）と Postgres の `users`（ロール・ステータス・業務データ）に分裂しており、`getSessionUser` の DB 同期、登録・退会・BAN 時の両側整合という「同期機構そのもの」がコア複雑性になっている
2. **`lib/crud` の二重アダプタ** — Drizzle 版と Firestore 版の 2 実装を維持しており、Firestore 版は機能制限が多い（OR 不可・orderBy 単一・belongsToMany 非対応等）。機能追加のたびに「Firestore 側どうする問題」が発生する
3. **フォーク毎のセットアップ 2 系統** — 下流プロジェクトを 1 つ生むたびに Firebase プロジェクト + Neon プロジェクト + 2 系統の環境変数が必要

## 拘束規律（封じ込めドクトリン）

維持を選んだ以上、慢性コストが**広がらない**よう以下を拘束ルールとする。

### 1. Firestore の役割は「リアルタイム配信チャネル」に限定する

- 新規ドメインは**原則 Drizzle（`dbEngine: "Neon"`）**
- Firestore を選べるのは、リアルタイム UX（チャット・プレゼンス・ゲーム状態配信等）が**本質要件**であるドメインのみ
- Firestore は「第二のデータベース」ではなく「配信インフラ」と再定義する。業務データ・集計対象データを Firestore に置く拡張は不可

### 2. `lib/crud` の Firestore アダプタは機能凍結する

- 現状の機能制限（`src/lib/crud/README.md` の「Firestore 版との差異」参照）を**仕様として凍結**し、以後の機能拡張は行わない
- Drizzle 側に機能を追加する際、Firestore 側は「無視 or エラー」の対応のみ行い、同等機能の実装は不要

### 3. Firebase 結合面の上限は「認証・ストレージ・配信」の 3 点とする

- この 3 点に留まる限り、将来もし乗り換えが必要になっても手術範囲は変わらない
- FCM・App Check 等の「残留配当」の採用は可（結合面の深化ではなくエコシステム内の収穫）
- 結合面を広げる方向の拡張（例: Firestore への業務データ配置、Firebase Functions へのロジック移設）は不可

### 4. ユーザー同期機構は「コア資産」として扱う

- Firebase Auth ↔ Postgres `users` の同期はこの構成の急所であり、ここのバグだけは致命傷になり得る
- 登録・退会・BAN・ロール変更など同期経路に触れる変更は、必ず両側の整合を検証する（USER_STATUS_HISTORY・audit 配線はこの防衛線の一部）

## ホットパス・リアルタイム層 (2026-08 追記)

Firestore 配信チャネルには**構造的な上限**があり、それを超える領域は BaaS の守備範囲外である
(per-doc 持続書き込み ~1write/秒、購読課金 = 書き込み × 購読者数)。
下流プロジェクトの本番環境（多人数が同時参加するイベント機能）で実障害 (500CCU で TX リトライストーム) が発生したことを受け、
第 3 のバックエンド層として **ルーム権威サーバー (servers/room, Cloudflare Durable Objects)** を追加した。

### 棲み分け基準

| 条件 | 使う層 |
|------|--------|
| 共有状態への書き込みが毎秒級で持続 / 購読ファンアウト数百超 / 閾値検知に単一TX意味論が必要 | servers/room (ルーム基盤) |
| それ未満の通常のリアルタイム UX (チャット・通知・per-user ドキュメント) | Firestore 配信 (規律 1 の通り) |
| 経済・権威データ (抽選・ウォレット・アイテム) | 従来通り PostgreSQL が唯一の権威 |

### 結合面の統制 (規律 3 の拡張)

- Cloudflare への結合は `servers/room/` に**限定**する。アプリ本体 (Next.js) の Cloudflare 移設や、
  Workers への業務ロジック一般の移設は不可 (本体は Vercel 維持 — OpenNext アダプタのラグ、
  firebase-admin 非互換、下流フォークの追随不能性による)
- 可逆性の担保: ルームロジックは純粋 reducer (`features/*/room/`)、transport は protocol で抽象化。
  ベンダー乗り換え時の手術範囲は `servers/room/src/core/` に限定される
- オプトイン既定無効。使わないフォークには依存・課金・ランタイム影響ゼロ (冪等運用は servers/room/README.md)

## 再評価トリガー

「ずっと大丈夫か」を常時悩まないため、以下のいずれかが発生した時点でこの決定を再評価する。

1. Firestore または Firebase Auth の**料金体系・提供条件の実質改悪**
2. ユーザー同期起因の障害が**繰り返し**発生し、保守コストが明らかに上振れしたとき
3. **次世代テンプレートを別系統として新設する**事業判断をしたとき
