# 設計思想とアーキテクチャ（コードの置き場所）

> **この文書が裏付ける CLAUDE.md の節**: CODE_PLACEMENT / STORES / DOMAINS（core と business の区別）
> 処理の流れ（8 層）は [アプリ構築における構成層](アプリ構築における構成層.md)、画面の分割は [UIレイヤーの概念とコンポーネント分割方法](UIレイヤーの概念とコンポーネント分割方法.md) を参照。

## 1. 概要

コードをどこに置くかを決めるための考え方。DDD（ドメイン駆動設計）の発想をもとに、フロントエンドを含むアプリ全体に広げている。

### 設計原則

- **ビジネスドメインごとに責務を閉じる**: 各ドメインは、自分の機能に必要なもの（エンティティ・サービス・フック・UI）を自分の中に持つ。ドメインを足すときも消すときも、そのフォルダを見れば済むようにするため
- **横方向の依存を管理する**: ドメイン同士・ドメインとライブラリの依存の向きを決めておく（§4）。向きが決まっていないと、どこを直すと何が壊れるかが追えなくなる
- **すべてが何かに所属する**: 「とりあえず置き場」を作らない（§5）

---

## 2. 3 つの級

コードは性質と規模で 3 つの **級** に分けて置く（処理の流れの「8 層」と区別するため、置き場所の区分は「級」と呼ぶ）。

| 級 | 説明 | 配置先 | 含められるもの |
|----|------|--------|----------------|
| ドメイン級 | ビジネス概念として独立 | `features/` | 全て（エンティティ、コンポーネント、フック、サービス、ストア等） |
| ライブラリ級 | どのアプリでも使える、複数ファイルの独立した機能群 | `lib/<機能名>/` | エンティティ以外の全て |
| ユニット級 | ライブラリにするほどではない小さな機能（複数ファイル可） | UI: `src/components/`<br>フック: `src/hooks/`<br>純粋関数: `src/utils/` | コンポーネント、フック、関数のみ |

### 判断フロー

```
Step 1: ビジネスドメインとして成立するか？
        → Yes: features/（ドメイン級）

Step 2: 複数ファイルで構成される独立した機能群か？
        → Yes: lib/<機能名>/（ライブラリ級）
        → ライブラリにするには過剰: 次へ

Step 3: サービスやストアを持たない小さな機能（ユニット級）
        → UI有り（フック・関数も含んでOK）: src/components/
        → フックのみ: src/hooks/
        → 純粋関数: src/utils/
```

## 3. それぞれの級

### 3.1 ドメイン級（`src/features/`）

テーマごとに完結した責務を持つ一連の機能群。目安は次のとおり。

- 独立したビジネス概念である（ユーザー、ウォレット、クーポン…）
- 多くはエンティティ（DB テーブル）とライフサイクル（作成・更新・削除）を持つ。ただし DB を持たないドメインもあり得る。決め手は「ビジネス概念として独立しているか」で、テーブルの有無ではない

**分ける理由**: ビジネスの概念ごとにまとまっていれば、仕様の変更がそのドメインの中で閉じる。機能の種類（全ドメインのフックを 1 か所、のような分け方）でまとめると、1 つの仕様変更のたびにあちこちのフォルダを触ることになる。

#### core ドメインと business ドメイン

- `features/core/`: upstream（ベーステンプレート）が提供する基盤ドメイン（auth, user, wallet 等）。手で保守する（`domain.json` を設定の置き場として持つものもあるが、`dc:generate` の対象ではない）。一覧は `src/features/core/README.md`。import は `@/features/<domain>` と書ける（tsconfig の paths で `core/` を省略）
- `features/`: fork で自由に追加するドメイン。`domain.json` から `dc:generate` で雛形を生成する

core ドメインはデータレイヤー（エンティティ・サービス・API・フック）までを持ち、画面のデザインは下流に任せる。下流ごとに見た目が違うのが前提なので、core に画面部品を入れると下流がそれを編集するしかなくなるためである。

### 3.2 ライブラリ級（`src/lib/`）

アプリケーションに依存しない、複数ファイルの独立した機能群。コンポーネント、フック、サービス、ストアなど、エンティティ以外は何でも含められる。何があって誰が作ったかは目録 `src/lib/CATALOG.md`、管理方法は `src/lib/README.md`。

- エンティティが必要ならドメインにする
- `features/` のドメインに依存しない（lib 同士の依存、npm パッケージ・Node.js API への依存は OK）
- 別のプロジェクトにそのまま持っていっても動く

**分ける理由**: ドメインを知らない部品として切り出しておくと、どのドメインからも同じ形で使え、テストもドメインのデータなしで書ける。ドメインの知識が混ざると、そのドメインを持たない fork では使えなくなる。

**所有はライブラリ単位**: ライブラリはプロジェクト内に置いた小さなパッケージのように扱う。`src/lib` というフォルダが upstream のものなのではなく、ライブラリ 1 つずつに持ち主（作ったリポジトリ）がいて、目録 `src/lib/CATALOG.md` の節がそれを表す。上流のライブラリは公開している入口だけを使い、中身の編集・削除はしない（変えたいときは上流に依頼する）。fork は自分のライブラリを自由に足してよく、目録の自分の節に 1 行足す。汎用的になった fork のライブラリは上流へ昇格させる。こうしておくと、上流の更新はライブラリの中だけで起き、fork のライブラリとは重ならないので、merge で衝突しない。

### 3.3 ユニット級（`src/components/` / `src/hooks/` / `src/utils/`）

ライブラリにするほどではない、比較的シンプルな機能・UI 部品。

- `components/`: 特定のドメインやライブラリに属さない汎用 UI。表示のためのロジック（フォーマット等）や、ローカル状態だけの自己完結したフックを含んでよい。子コンポーネントやフックへの分割も推奨
- `hooks/`: 単体で完結する汎用フック（補助ファイルに分けてもよい）
- `utils/`: 副作用のない、React に依存しない純粋関数

ロジックが大きくなったり、サービスやストアが必要になったりしたらライブラリ級に上げる。対応するストアやサービスがあるフックは、そのライブラリかドメインに所属させる。

**分ける理由**: 小さな部品のたびにライブラリのフォルダを作ると、索引が埋もれて探しにくくなる。逆にユニット級に大きな機能を置くと、関連するファイルが散らばる。

### 3.4 どこにも属さないページ専用の部品

サービス説明のページなど、どのドメインにも属さず、汎用化の必要もなく、そのページでしか使わない部品は、そのルートのディレクトリの中に置く。置き場所はルートの持ち主で決まる。

- upstream が作ったルートの既定画面の部品 → `_screen/`（Screen の隣。フラットでもサブディレクトリでもよい）
- fork が自分の画面・ページ専用部品を足す場合 → `_components/`（下流専用。upstream は自分のルートの `_components/` に何も置かない）

後で再利用されるようになったら、`src/components`（複数ドメイン）や `features/<domain>/components`（単一ドメイン）に移す。

持ち主でフォルダを分けているのは、下流が upstream のファイルを編集せずに画面を差し替えられるようにするためである（`_screen/` は upstream が更新し続け、`_components/` は下流だけが触る）。ページの構造と差し替え手順は [UIレイヤーの概念とコンポーネント分割方法](UIレイヤーの概念とコンポーネント分割方法.md) §2 と `src/lib/screens/README.md` を参照。

## 4. 依存の向き

```
features ──→ lib ──→ （npm パッケージ・Node.js API）
   │          ↑
   │        lib 同士は OK
   ↓
features 同士: UI 側はフック経由 / サーバー側は直接 OK（循環禁止）
```

### lib → features は禁止

lib は「どのアプリにも持っていける部品」として作る。lib がドメインを import すると、そのドメインがないと動かなくなり、汎用部品ではなくなる。ドメインの処理を lib に差し込みたいときは、lib 側に登録口（レジストリやコールバック引数）を用意し、ドメイン側から登録する（例: `lib/crud` は監査ログのドメインを知らず、各ドメインが `createCrudService` の `audit.recorder` に `auditLogger` を渡す）。

### UI 側: 他ドメインのデータは、そのドメインのフックで取る

別ドメインのデータが欲しいとき、自分のドメインに専用のフックやクライアントサービスを作って API を叩いてはいけない。参照先ドメインが提供するフックを使う。
同じデータの取得口が複数あると、SWR のキャッシュキーが分かれて片方の更新がもう片方に反映されず、API の変更時にも直す場所が散らばるためである。

### サーバー側: 他ドメインのサービスを直接呼んでよい

サーバー内で別ドメインの API を HTTP で叩くのは、認証・シリアライズの往復が無駄なだけなので、サービスを直接 import する。ただし循環依存（A → B → A）は禁止。循環が必要に見えるときは、責務の切り方が間違っているか、共通部分を lib に出すべきサインである。

## 5. グローバルな定義を置かない

`src/types/` や `src/constants/` のような「とりあえず置き場」は作らない。型・定数は、それを使うドメインかライブラリに所属させる。
置き場を作ると、何でもそこに入れられて所属が曖昧になり、どのドメインを消すと何が不要になるのかが分からなくなる。責務を切り分けられていれば、所属先は自然に決まる。

例外として次のトップレベルは存在するが、いずれも「何でも置き場」ではなく役割が決まっている。

- `src/stores/`: アプリ全体で共有する状態だけ（サイトテーマ、管理画面レイアウトなど）。ドメイン固有のストアは `features/<domain>/stores/` に置く（`src/stores/README.md`）
- `src/config/`: 下流が値を書き換える設定値だけ。ロジックは置かない
- `src/registry/`: 業務ドメインを全体で扱うための一覧（ドメインを 1 つ作ると 1 行増える生成物。serviceRegistry は `domainEntry.ts` から）。下流の登録口ではない（`src/registry/README.md`）。機能ごとの差し込みは持ち主のフォルダの受け口（`scripts/extensions/README.md`）
