# エラーハンドリング方針

> **この文書が裏付ける CLAUDE.md の節**: ERROR_HANDLING / PROHIBITED（normalizeHttpError の省略禁止）
> **関数ごとの使い方**: [src/lib/errors/README.md](../../src/lib/errors/README.md)

サーバーからクライアントまで、エラーが層をまたいでどう流れるか、なぜその形にしているかをまとめる。

## 1. 流れ

```
サーバーサービス   ── DomainError(message, status) を throw
      ↓
API ルート         ── routeFactory が { message } + status の JSON に変換
      ↓ HTTP
クライアントサービス ── normalizeHttpError で HttpError に統一して throw
      ↓
フック            ── HttpError をそのまま渡す（加工しない）
      ↓
UI               ── err(error, fallback) で文言を決め、トースト・フォームに出す
```

型は 2 種類しかない。サーバー側は `DomainError`、クライアント側は `HttpError`。この 2 つの間は HTTP の JSON `{ message }` だけでつながる。

## 2. なぜこの形か

**ユーザー向けの文言を決めるのはサーバーサービスだけ。**
ビジネスルールを知っているのはサーバーサービスなので、「何が起きたか」をユーザー向けに書けるのもそこだけである。`DomainError` の `message` は日本語で、ユーザーが次の行動を取れる文言にする。こうしておくと、クライアント側は届いた `message` をそのまま表示すればよく、同じ文言を画面ごとに書き直す必要がない。

**クライアント側でエラーの形を 1 種類に揃える。**
axios の例外、外部 SDK の例外、ブラウザ API の失敗は、それぞれ形が違う。これを UI で個別に判定し始めると、画面ごとに分岐が増え、扱いが揃わなくなる。そこで、クライアントサービスの出口で必ず `HttpError` に揃える（`normalizeHttpError`）。HTTP を介さない失敗はフックや部品の側で `createHttpError` を使って同じ形にする。UI は「`HttpError` が来る」という前提だけで書ける。

**UI は文言の決定だけを行う。**
UI の仕事は「サーバーが返した文言があればそれを、なければ画面ごとのフォールバックを出す」ことだけで、`err(error, fallback)` がそれを 1 行で行う。ステータスによって表示を変えたいとき（409 で重複を案内する等）だけ `status` を見る。

**フックはエラーを加工しない。**
フックが文言を書き換えたりトーストを出したりすると、同じフックを使う別の画面で表示を変えられなくなる。通知の出し方は UI の責務とし、フックは `HttpError` をそのまま返す（UI 通知の責務分担は [UIレイヤーの概念とコンポーネント分割方法](UIレイヤーの概念とコンポーネント分割方法.md) §6）。

## 3. 想定外の例外の扱い

`DomainError` 以外の例外（ライブラリ・DB・コードの不具合）は、サーバーサービスで握りつぶさずに上へ伝える。API ルート（routeFactory）がログに残し、500 として返す。

想定外の例外のメッセージにはライブラリや SQL の内部情報が含まれ得るため、方針としては **詳細はサーバーのログにだけ残し、クライアントには汎用の文言だけを返す**。

routeFactory（`createApiRoute`。`createDomainRoute` / `createMeRoute` / `createDeviceRoute` もこれを経由する）は、`DomainError` 以外の例外を `{ message: "サーバーでエラーが発生しました" }` + 500 で返し、詳細は `console.error` に残す。ユーザーに伝えたい失敗は必ず `DomainError` で throw すること（素の `Error` の文言は画面に届かない）。

## 4. 層ごとの責務

| 層 | やること | やらないこと |
|---|---|---|
| サーバーサービス | ユーザーへ伝える失敗を `DomainError` で throw（`status` + 日本語 `message`） | 想定外の例外を握りつぶす |
| API ルート | routeFactory に任せる（変換・ログは自動） | `DomainError` を新たに throw する、独自の JSON 形式を返す |
| クライアントサービス | `catch` で `normalizeHttpError(error, fallback)` を通して throw | 生の例外を上に渡す |
| フック | `HttpError` をそのまま返す。HTTP 外の失敗は `createHttpError` で作る | 文言の書き換え、トースト表示 |
| UI | `err(error, fallback)` で文言を決めて表示する | HTTP の詳細（axios の構造など）を判定する |

アプリ全体のログ送信・監視は、UI に書かずに `setApiErrorHandler` / `registerCrudEventHandler` に登録する（[src/lib/errors/README.md](../../src/lib/errors/README.md)）。
