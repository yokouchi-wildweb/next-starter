# アプリ構築における構成層（8 層）

> **この文書が裏付ける CLAUDE.md の節**: ARCHITECTURE / API_ROUTES（ファクトリー必須）/ PROHIBITED（層をまたぐ禁止事項）
> コードの置き場所（features / lib / unit）は [設計思想とアーキテクチャ](設計思想とアーキテクチャ.md)、画面の分割は [UIレイヤーの概念とコンポーネント分割方法](UIレイヤーの概念とコンポーネント分割方法.md)、エラーの流れは [エラーハンドリング方針](エラーハンドリング方針.md) を参照。

リクエストがページから DB まで通る道筋を 8 つの層に分け、それぞれが何を担い、なぜそこに境界を置いているかをまとめる。

## 1. 全体の流れ

```
                          ┌──────────────── サーバー ────────────────┐
1. ページ層 (page.tsx → _screen/)  ── SSR: loader が直接 ──→ 6. サーバーサービス
      ↓                                                          ↓
2. UIコンポーネント層                                         7. エンティティ
      ↓                                                          ↓
3. フック層                                                   8. データベース
      ↓                                                          ↑
4. クライアントサービス層 ── HTTP(axios) ──→ 5. APIルート層 ──────┘
   └──────── クライアント ────────┘
```

データの経路は 2 本しかない。

- **初回描画（SSR）**: ページ層の loader がサーバーサービスを直接呼ぶ。HTTP を挟まない
- **クライアントからの取得・更新**: フック → クライアントサービス → HTTP → API ルート → サーバーサービス

どちらの経路も、DB に触れるのはサーバーサービスだけである。

1 つのドメインの中では、層がそのままフォルダに対応する。

```
src/features/<domain>/
  components/       … 2. UIコンポーネント層
  hooks/            … 3. フック層
  services/client/  … 4. クライアントサービス層
  services/server/  … 6. サーバーサービス層
  entities/         … 7. エンティティ層
src/app/<route>/    … 1. ページ層（page.tsx / _screen/）
src/app/api/**      … 5. APIルート層
```

## 2. 各層の責務と境界の理由

### 1. ページ層（`page.tsx` → `_screen/<Name>Screen.tsx` + `_screen/loader.ts`）

**担うこと**: URL ごとの入口。loader が初回描画に必要なデータを取り、redirect / notFound を判断する。Screen が loader の結果を受け取り、セクションコンテナを並べる。

**境界の理由**: `page.tsx` は Screen への 1 行スイッチにして、ロジックを一切置かない。下流は page.tsx の向き先を自分の Screen（`_components/`）に変えるだけで画面を差し替えられ、そのとき loader はそのまま使い回せる。page.tsx にデータ取得を書くと、画面を差し替えた下流がその処理を写すか upstream のファイルを編集するしかなくなる。
Screen は `"use client"` を付けず、フックも state も持たない。サーバーで描画されることで、loader の結果を props として受け取れる。

**破ると壊れるもの**: 下流による画面の差し替え（`pnpm test:screens` が page.tsx・Screen・loader の形を検査する）。詳細は `src/lib/screens/README.md`。

### 2. UIコンポーネント層（`features/<domain>/components/`）

**担うこと**: 表示・入力・イベント発火。処理の結果を受けた通知（トースト）・画面遷移など、UI に密着した処理。

**境界の理由**: UI は通信の知識（エンドポイントのパス、HTTP クライアント、クライアントサービス）を持たず、フックだけを呼ぶ。同じデータを画面ごとに取り直す書き方を防ぎ、SWR のキャッシュ共有と mutation の並行実行の安全性（`useDomainMutation`）を必ず通すためである。

**破ると壊れるもの**: キャッシュの一貫性（ある画面で更新しても別の画面が古いまま）。UI からクライアントサービスを直接 import すると lint `client-service-boundary/no-direct-import` が検出する。

### 3. フック層（`features/<domain>/hooks/`）

**担うこと**: クライアントの状態管理（読み込み中・エラー・キャッシュ）と、クライアントサービスの呼び出し。

**境界の理由**: フックは「データの取得・更新とその状態」だけを扱い、トーストやモーダルなどの通知を持たない。通知をフックに入れると、そのフックを使うすべての画面が同じ通知を出すことになり、画面ごとに出し方を変えられなくなる。エラーも加工せず `HttpError` のまま返す。

**破ると壊れるもの**: 再利用性。フックからサーバーサービスを import すると、サーバー専用のコードがクライアントに入りビルドが壊れる。

### 4. クライアントサービス層（`features/<domain>/services/client/`）

**担うこと**: HTTP 通信を 1 か所に集める。エンドポイント・メソッド・パラメータの組み立てと、例外の `HttpError` への正規化。

**境界の理由**: クライアントでは axios だけを使い、通信はこの層にしか書かない。通信の詳細（パス、ヘッダー、エラーの形）が変わったときに直す場所を 1 つにするためである。`normalizeHttpError` を必ず通すことで、上の層は例外の種類を気にしなくてよくなる。

**破ると壊れるもの**: エラー表示の一貫性と、API 変更時の修正範囲。

> 例外: SSE などストリーミングのエンドポイントだけは `fetch` + `ReadableStream` を使ってよい（axios はブラウザでストリームを読めない）。それでも通信はクライアントサービスに置く。

### 5. APIルート層（`src/app/api/**`）

**担うこと**: HTTP の入口。リクエストを受け取り、サーバーサービスを呼び、結果を JSON で返す。**受け取る → 呼ぶ → 返す** 以上のことはしない。

**境界の理由**: すべての API ルートは routeFactory のファクトリー（`createApiRoute` / `createDomainRoute` / `createMeRoute` / `createDeviceRoute`。設定済み版を `@/wiring/apiRoute` から import する）のどれかで作る。認可（`access` は型で必須。汎用の `/api/[domain]` でアクセス設定の無いドメインは管理者限定に倒れる）、ログイン中の利用者の取得（1 回だけ DB 同期で解いて `ctx.user` で渡す）、`DomainError` の変換、監査ログのコンテキスト、デモモードの制御がファクトリーに集まっているので、ルートごとに書き忘れることがない。ビジネスロジックや DB 操作をここに書くと、同じ処理を SSR（loader）から呼べなくなり、権限チェックなどの共通処理も散らばる。

```ts
import { createApiRoute } from "@/wiring/apiRoute";

export const GET = createApiRoute(
  { operation: "GET /api/example", operationType: "read", access: "authenticated" },
  async (req, { user }) => exampleService.getForUser(user.userId),
);
```

**破ると壊れるもの**: 認可。ファクトリーを通さないルートは認可の強制から外れる。本人のデータだけを返すルートは `createMeRoute`（`/api/me/**`）で作り、サーバー側で `user.userId` に絞る（クライアントが渡す ID を信用しない）。詳細は `src/lib/routeFactory/README.md`。

### 6. サーバーサービス層（`features/<domain>/services/server/`）

**担うこと**: ビジネスルール、永続化、トランザクション、外部サービスとの連携。ユーザーへ伝える失敗を `DomainError` で throw する。

**境界の理由**: ビジネスロジックと DB アクセスをこの層に閉じ込めることで、API ルート（クライアントからの経路）と loader（SSR の経路）が同じ処理を共有できる。汎用の CRUD は `createCrudService`（`src/lib/crud`）が提供し、ドメイン固有の振る舞いは `wrappers/` で前後に足す。

**破ると壊れるもの**: 2 つの経路の挙動の一致。

### 7. エンティティ層（`features/<domain>/entities/`）

**担うこと**: データの形の正規の定義。Drizzle のテーブル（`drizzle.ts`）、サーバー用の Zod スキーマ（`schema.ts`）、その `z.infer` 型（`form.ts`）、ドメインモデルの型（`model.ts`）。

**境界の理由**: エンティティは全層から参照されるので、特定のフォームや画面の都合を持ち込まない。フォーム固有の入力ルールはそのフォームの隣の `formEntities.ts` に置く。business ドメインのエンティティは `dc:generate` が生成するので、手で編集しない。

**破ると壊れるもの**: サーバー側からの再利用。エンティティが UI に依存すると、サーバーサービスや API から使えなくなる。

### 8. データベース層

PostgreSQL（Neon、Drizzle 経由）が正のデータを持つ。Firestore はリアルタイム配信のための補助（[バックエンド構成ドクトリン](バックエンド構成ドクトリン.md)）。どちらもサーバーサービス以外からは触らない。

**破ると壊れるもの**: 監査・権限チェック・キャッシュの無効化。これらはサーバーサービス（`createCrudService`）の書き込み経路に組み込まれているので、それ以外から DB を書き換えると素通りする。

## 3. よくある判断

| ケース | 可否 | 理由 |
| --- | --- | --- |
| `page.tsx` にデータ取得や redirect を書く | ❌ | page.tsx は 1 行スイッチ。`_screen/loader.ts` に置けば、下流が Screen を差し替えても同じ loader を使える |
| `_screen/loader.ts` からサーバーサービスを呼ぶ | ✅ | 同じサーバー内で完結する。API ルートと同じサービスを呼ぶので、2 つの経路の結果が一致する |
| UI から `xxxClient` を import して呼ぶ | ❌ | フックを挟まないと、SWR のキャッシュ共有と mutation の並行実行の安全性が効かない（lint が検出） |
| フックからサーバーサービスを呼ぶ | ❌ | サーバー専用コードがクライアントに入り、ビルドが壊れる |
| UI やフックで `fetch` / axios を直接書く | ❌ | 通信はクライアントサービスに集める。直す場所が散らばり、エラーの正規化も漏れる |
| API ルートで Drizzle を直接使う | ❌ | DB アクセスはサーバーサービスに閉じ込める。loader から同じ処理を呼べなくなる |
| フックからクライアントサービスを呼ぶ | ✅ | 正しい経路 |
| フックでトーストを出す | ❌ | 通知は UI の責務。フックを使うすべての画面が同じ通知を出すことになる |
| エンティティにフォーム固有のスキーマを置く | ❌ | フォームの隣の `formEntities.ts` へ。エンティティは全層の共有物 |
| routeFactory を使わずにハンドラを export する | ❌ | 認可・エラー変換・監査コンテキストから外れる |
