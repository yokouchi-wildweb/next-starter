# アーキテクチャの全体像

このリポジトリの設計を 1 枚で把握するための文書。各テーマの「なぜそうするか」は、ここからリンクする個別の文書に書いてある。

- **ルールの索引**（何をする / しない）は、ルートの `CLAUDE.md`。エージェントは毎セッションこれを読む
- **使い方・契約**（API、オプション、手順）は、コードの隣の `README.md`
- **この `!must-read/`** は、ルールの背景（なぜそうするか、何を避けたいか）を書く場所。ルールの解釈に迷ったときと、設計思想を理解したいときに読む

---

## 1. このリポジトリは何か

多数の派生プロジェクト（fork）の土台になる **上流テンプレート**（Tier1）である。fork はこのリポジトリを取り込んで自分のサービスを作り、上流の更新を継続的に merge する。

この前提から、設計全体に通じる 2 つの方針が出てくる。

- **下流が上流のファイルを編集せずに済むようにする。** fork が上流のファイルを書き換えると、上流を merge するたびに衝突する。そこで上流は「構造と既定値」だけを持ち、fork が変えたい部分には差し替え口（設定ファイル、登録口、画面の切り替え）を用意する
- **汎用的なものは上流に置く。** 複数の fork で必要になる機能を各 fork が個別に作ると、同じものが何度も作られ、それぞれ違う形に育つ。汎用機能は上流に置き、fork はそれを使う（fork から上流への依頼は `/upreq`、上流から fork への追随依頼は `.notices/`）

開発は主に AI エージェントが行う。そのため、ルールはエージェントが毎回読む `CLAUDE.md` に集め、ルールを守れているかはできるだけ lint とテストで機械的に検査する。

## 2. 設計の 4 つの軸

```
             置き場所（どこに置くか）            処理の流れ（どう通るか）
          ┌─────────────────────────┐      ┌───────────────────────────┐
          │ features/  ドメイン       │      │ ページ → UI → フック        │
          │ lib/       ライブラリ     │  ×   │ → クライアントサービス → API │
          │ components/ hooks/ utils/ │      │ → サーバーサービス → DB      │
          └─────────────────────────┘      └───────────────────────────┘
                                                  │ ページと UI の内側
                                                  ↓
          バックエンド（何に保存するか）       画面の分割（どう組むか）
          ┌─────────────────────────┐      ┌───────────────────────────┐
          │ PostgreSQL が正のデータ    │      │ ページ（Screen + loader）  │
          │ Firebase は認証・Storage・ │      │ → セクションコンテナ        │
          │ リアルタイム配信だけ       │      │ → 部品                     │
          └─────────────────────────┘      └───────────────────────────┘
```

### 置き場所: 3 つの級（[設計思想とアーキテクチャ](設計思想とアーキテクチャ.md)）

コードは規模と性質で 3 つの級（ドメイン級・ライブラリ級・ユニット級）に分けて置く。ビジネス概念として独立していれば `features/<domain>/`（エンティティ・サービス・フック・UI をすべて持つ）、複数ファイルの汎用機能なら `lib/<name>/`（ドメインに依存しない）、それ以下の小さな部品は `components/` / `hooks/` / `utils/`。
依存の向きは `features → lib` の一方向で、lib はドメインを知らない。グローバルな「何でも置き場」は作らず、すべてのコードを何かに所属させる。

### 処理の流れ: 8 層（[アプリ構築における構成層](アプリ構築における構成層.md)）

1 つのリクエストは、ページ → UI → フック → クライアントサービス → API ルート → サーバーサービス → エンティティ → DB の順に通る。初回描画だけはページの loader がサーバーサービスを直接呼ぶ。
各層の境界は「同じことを書く場所を 1 つにする」ためにある。通信はクライアントサービス、ビジネスロジックと DB アクセスはサーバーサービス、という具合に集めておくと、変更のときに直す場所が 1 つで済み、SSR とクライアントの 2 つの経路が同じ処理を共有できる。

### 画面の分割: 3 つの UI レイヤー（[UIレイヤーの概念とコンポーネント分割方法](UIレイヤーの概念とコンポーネント分割方法.md)）

ページ層と UI 層の内側を、ページ（`page.tsx` → `_screen/<Name>Screen.tsx` + `loader.ts`）・セクションコンテナ・部品の 3 つに分ける。
`page.tsx` は Screen への 1 行スイッチで、fork は向き先を自分の Screen に変えるだけで画面を作り直せる。フックはセクションコンテナが呼び、部品には props で渡す。初回描画に見えるデータは loader が取り、フックの `fallbackData` につなぐ。

### バックエンド: PostgreSQL が正（[バックエンド構成ドクトリン](バックエンド構成ドクトリン.md)）

業務データはすべて PostgreSQL（Neon、Drizzle 経由）に置く。Firebase は認証・ファイル保存・リアルタイム配信の 3 つに限定し、業務データやロジックを置かない。高頻度のリアルタイム処理は Firestore ではなく、別建てのリアルタイムサーバー（`servers/room/`）が担う。
Supabase への一本化を検討したうえで採らなかった理由と、この構成を見直す条件もこの文書にある。

## 3. 横断する仕組み

4 つの軸の上で、どのドメインからも使う仕組み。新しい機能を作る前に、ここで足りないかを先に確認する（同じものを作り直さないため）。

| 仕組み | 何のためにあるか | 詳細 |
|---|---|---|
| コード生成（`dc:generate`） | business ドメインのエンティティ・サービス・フック・管理画面を `domain.json` から生成する。生成物は手で編集せず、`wrappers/` などの差し替え口で拡張する | `scripts/domain-config/README.md`、`src/features/README.md` |
| 汎用 CRUD（`createCrudService`） | 一覧・検索・作成・更新・削除・並び替えなどを全ドメイン共通の実装で提供する。ドメインごとの差分だけを書けば済む | `src/lib/crud/README.md` |
| API ルートのファクトリー（routeFactory） | すべての API ルートを 3 つのファクトリーのどれかで作り、認可・エラー変換・監査のコンテキストを強制する。認可の指定漏れは許可ではなく拒否に倒れる | `src/lib/routeFactory/README.md` |
| エラーの流れ | サーバーは `DomainError`、クライアントは `HttpError` の 2 種類だけ。ユーザー向けの文言はサーバーサービスが決め、UI はそれを表示するだけ | [エラーハンドリング方針](エラーハンドリング方針.md) |
| 認証と認可ガード | JWT セッションと、proxy → layout → loader の 3 段のガード。ロール・ステータスによる判定は必ず DB と同期した値（`getSessionUser` / `authGuard`）で行う。JWT だけの軽い取得（`getTokenOnlySession`）は監査の記録者やデモ判定など、拒否に使わない用途に限る。JWT の中身は発行後に古くなり得るため | `src/features/core/auth/README.md` |
| 登録表（registry） | `src/registry/` は「業務ドメインを全体で扱うため、ドメインを 1 つ作ると 1 行増える一覧」（serviceRegistry・schemaRegistry・domainConfigRegistry など。生成物か、core は手書き）。serviceRegistry はドメイン名からサービス・表・主キーを引く正式な仕組みで、各ドメインの `services/server/domainEntry.ts` から生成する。特定ドメインの拡張口（下流が追記するもの）も同じフォルダにあるが、役割は別 | `src/lib/domain/README.md`、各 registry ファイルの冒頭コメント |
| proxy | リクエストごとの前処理（メンテナンス・デモモード・機能ゲート・リダイレクト）をハンドラの連鎖で行う | `CLAUDE.md` PROXY、`src/proxies/` |
| 監査ログ・定期処理・集計 | 監査ログ（`auditLog`）、cron とタスクランナー（`lib/cron`）、カウンタ・DAU・集計キャッシュ（`userCounter` / `interactionTracking` / `analytics`）など、運用に必要な基盤 | 各ドメインの README、`CLAUDE.md` の該当節 |

## 4. 上流と下流の所有分担

上流がファイルを更新しても fork の変更が消えないように、ファイルごとに「誰が書くか」を決めている。原則は **上流 = 構造、下流 = 値**。

| 対象 | 上流が持つもの | 下流が持つもの |
|---|---|---|
| 画面 | 既定の画面（`_screen/`）、loader | `page.tsx` の向き先、差し替えた画面と専用部品（`_components/`） |
| スタイル | トークンの構造（`theme.css`）と既定値（`*.defaults.css`） | 変えたい値だけ（`src/styles/custom/**`） |
| UI の設定 | 部品の既定値とその型 | 上書きする値（`src/config/ui/*.config.ts`） |
| 拡張 | 登録表の構造と生成器（`src/registry/*`）、core の `domainEntry.ts` | 業務ドメインの `domain.json`（→ 生成）、core の access を変える `domainEntry.override.ts`、特定ドメインの拡張口に登録する中身 |
| ルール | `CLAUDE.md`（全 fork 共通） | `.claude/rules/project.md`（fork ごとの差分） |

core ドメイン（`src/features/core/`）は画面部品を持たず、データレイヤーまでにとどめる（理由は [設計思想とアーキテクチャ](設計思想とアーキテクチャ.md) §3.1）。

上流の変更で fork 側に作業が必要になるときは、変更と同じコミットで `.notices/` に通知を出す。fork は `/flux` で未適用の通知を順に取り込む（`.notices/README.md`）。

詳細: スタイルは `src/styles/README.md`、画面の差し替えは `src/lib/screens/README.md`、上流ファイルの編集可否は `CLAUDE.md` CORE_FILES。

## 5. 文書の地図

| 場所 | 中身 | 読むとき |
|---|---|---|
| `CLAUDE.md` | ルールの索引（英語・圧縮形式。全 fork 共通） | 毎セッション自動で読まれる |
| `.claude/rules/project.md` | その fork だけのルールと地図（upstream との差分） | 毎セッション自動で読まれる |
| `.notices/` | 上流の変更で fork 側に必要な追随作業の通知 | 上流を取り込むとき（`/flux`） |
| `docs/!must-read/`（ここ） | ルールの背景と設計思想 | 全体を理解したいとき、ルールの解釈に迷ったとき |
| コード隣の `README.md` | 各ライブラリ・ドメインの使い方と契約 | そのコードを使う・直すとき |
| `docs/setup/` | 外部サービス（Neon・Firebase・GCP など）の管理画面での設定手順 | fork の立ち上げ時（[新規プロジェクトの立ち上げ_フォークからデプロイまで](../setup/新規プロジェクトの立ち上げ_フォークからデプロイまで.md)） |
| `docs/journal/` | 日付付きの記録（障害の経緯、検証、決定の経緯） | 過去の経緯を調べるとき |

`docs/` にはこの 3 フォルダ以外を作らない。特定の機能やドメインについての文書は、そのコードの隣の README に書く。
