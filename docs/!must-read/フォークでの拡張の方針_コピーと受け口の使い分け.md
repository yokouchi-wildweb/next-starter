# フォークでの拡張の方針: コピーと受け口の使い分け

fork が上流の画面や処理を変えたいときに、コピーしてよいのか、上流に受け口を頼むのかを決める方針の、理由と背景をまとめた文書です。判定の手順は [`.claude/rules/core/extensions.md`](../../.claude/rules/core/extensions.md) にだけあり、ここには書きません。

## 原則

上流は仕組みを用意する。fork は見た目も機能も自由に作れる。ただし、自分が変えない処理は写さない。

## なぜ行数で決めないのか

問題はコピーの大きさではなく、上流の修正が届かなくなることです。

- 長い画面でも、中身が見た目と並べ方だけなら、古くなっても見た目がずれるだけで済みます
- 短いコピーでも、送信処理や rateLimit が入っていれば、上流の不具合修正や守りの強化がその fork に届きません

そのため、コピーに何が付いてくるかで決めます。開閉や hover のような見た目のための state は、見た目の側に含めます（state を一律に処理と数えると窮屈なため）。

## 守りの処理を別に扱う理由

access・rateLimit・recaptcha・セッション cookie・トークン発行・残高や決済の書き込みは、古くなると事故につながります。そのためコピーを認めません。

判断は領域の名前ではなく、コピーの中身で決めます。

- 認証画面でも、文言や見た目を変えるだけなら通常の扱いです
- 禁止するのはコピーだけです。fork の route が Factory に宣言すること、`walletService` を呼ぶこと、新しい認証手段を作ることは自由です

## 例

| やりたいこと | 扱い |
|---|---|
| 登録フォームの同意文にリンクを足す | 値の問題。フォームをコピーせず、値を上流に頼む |
| 登録の後にボーナスを付ける | route をコピーすると守りが付いてくる。上流が受け口を作り、守りの後で呼ぶ |
| ヘッダーの並びを変える | 見た目と並べ方だけならコピーしてよい |
| LINE ログインを新しく作る | 新機能なのでコピーに当たらない |

## 受け口を増やしすぎない理由

受け口は上流が守り続ける約束になるので、実際に使う機能のある依頼にだけ作ります。fork の数では絞りません。名前付き ReactNode を core に置かないのも、この約束を増やさないためです。

## 前例

- **Shopify**: checkout だけ別扱いにしている、調べた範囲で唯一の明確な方針。守りの処理を別に扱う根拠
- **WooCommerce・Docusaurus・shadcn**: コピーを禁じず、見える形にする。コピーの印の根拠
- **Django・Docusaurus**: 変えない部分を継承する、または包むことを、丸ごとの差し替えより優先する

## 不採用の案

| 案 | 採らない理由 |
|---|---|
| 行数で線を引く | 問題の所在と合わない |
| 認証・課金の領域のコピーを一律に禁止する | fork の正当な新機能まで止まる |
| コピーの台帳を持つ | 登録の手間がかかり、すぐ古くなる |
| 印に sha を持つ | merge-base で引けるので要らない |
| コピーを検査で止める | 見た目のコピーの更新は fork の判断でよい。印のないコピーは検出できないと割り切る |
| 受け口の数に上限を置く | 必要な口まで止めてしまう |
